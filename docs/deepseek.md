# 效率护城河：DeepSeek 如何重写 AI 的 Scaling 剧本

在过去将近十年里，整个人工智能行业一直被一条昂贵得令人咋舌的信条所统治：算力越大，模型越好。头部实验室往庞大的 GPU 集群里砸了上百亿美元，烧掉一座小城市的用电量，只为从稠密神经网络架构里挤出一点增量。圈子里默认的共识是，通往 AGI 的路就只能靠暴力堆算力——这本身就成了一个用资本垒起来的准入门槛。

DeepSeek 走的路，恰恰是对这套暴力共识的清醒偏离。当整个行业都在做更大的锤子时，DeepSeek 在重新思考钉子的物理结构。它把重心放在架构效率与全栈协同设计上，而不是拼谁的资源烧得多，从而直接挑战了「力大砖飞」的叙事。它的演进轨迹不只是技术上的好奇心使然，更代表了一种「通过优化获取智能」的方向，这场实验正在考验那些更大竞争对手在经济上能否持续。

一间实验室是怎么挑战巨头们的 scaling law 的？靠的不是某一次孤立的突破，而是一连串贯穿每一层技术栈的创新——从专家的组织方式，到模型的训练与推理方式，全都优化了一遍。DeepSeek 把效率当成武器，筑起了一条基于单位经济学而非单纯集群规模上的护城河。

下面就是这段崛起背后的技术路线图：一系列瓶颈、压缩手法和全栈设计决策，它们共同把效率变成了一种策略。

## DeepSeek 路线图：一系列 Scaling 瓶颈的解决史

理解 DeepSeek 技术路线图的最简洁方式，就是把它看成一连串瓶颈的清除过程。每一篇论文瞄准的都是一个不同的约束——当模型在更低的成本下追求更高能力时，这些约束就会暴露出来：稠密参数激活、薄弱的领域结构、KV-cache 的增长、MoE 训练的不稳定性、推理轨迹的成本，以及百万 token 级别的记忆。

这条进化路径的逻辑不是「把每个模型做大」，而是：让容量变稀疏，让数据具备领域形态，压缩注意力记忆，让前沿 MoE 训练稳定下来，通过可验证的强化学习诱导出推理能力，然后重新设计长上下文记忆，让推理不至于被自己的上下文淹没。

这个叙事框架很重要，因为它把文章保持在技术轨道上。下面每一节都围绕同样的三个问题展开：什么东西在制约？用什么机制化解了其中一部分？又剩下了哪些新的约束？

## 用压缩的视角看 DeepSeek 路线图

DeepSeek 的路线图也可以从另一个角度来理解：它是一连串尝试，试图在提升模型有效能力的同时，控制住三个不断膨胀的轴——参数/隐容量、序列/上下文长度、以及推理轨迹长度。

SVD 的直觉在这里很有用。Transformer 的一层，大体上是一堆可学习的线性映射加上非线性路由、门控、归一化和注意力。从一个线性映射来看，把权重矩阵看成 $W = U \Sigma V^\top$ 是个很好的概念模型：输入跟学到的方向做相关，奇异值放大或抑制这些方向，输出在另一个学到的特征基中重建。增宽模型或增大 FFN 维度，就等于增加这些方向的数量和丰富程度。这就是容量的 scaling。如果每个 token 无时无刻不在使用所有方向，成本就跟容量成正比增长。

这正是 DeepSeekMoE 的切入点。它不让每个 token 激活整个参数基，而是把每个 token 路由给一部分专家。细粒度专家切分提高了路由分辨率，共享专家则为频繁出现的特征提供了一条公共通路。这不是对特征空间的硬分解。它也不能保证公共特征梯度只流到共享专家那里。更准确的理解是，它提供了一种软的架构先验：让公共结构在共享专家那里被自然地学到，而把路由专家留给残差型的专业化。

![小黑把粗专家拆成细颗粒专家和共享专家](/books/mlsys/assets/deepseek-roadmap-illustrations/02-moe-sparse-capacity.png)

DeepSeek-Coder 和 DeepSeekMath 主要不是关于压缩的；它们是关于让学到的特征空间在特定领域中变得有用。用前面的语言来说，它们改变的是奇异方向被训练去代表什么。仓库级别的代码预训练教会模型的是软件结构特征：函数、API、import、测试、跨文件惯例。数学继续训练和 GRPO 教会模型的是符号化和推理导向的方向。容量不是抽象的；只有当数据分布和目标函数暴露出了正确的结构，表征基才会有用。

![小黑把通用语料分拣成代码结构和数学推理链](/books/mlsys/assets/deepseek-roadmap-illustrations/03-domain-code-math.png)

DeepSeek-V2 引入了第二个轴：序列/上下文维度。MLA 主要压缩的不是 token 的数量。它沿隐/通道维度压缩的是每个 token 的缓存 KV 表征。标准注意力会为每个 token、每一层存储一个很大的 K/V 表征。MLA 说的是：多头 K/V 信息中大量都是冗余的，因为每个头的 K/V 向量都是从同一个 hidden state 投影出来的。所以与其缓存完整展开的 K/V 状态，不如缓存一个更小的隐 KV 状态。MoE 稀疏化的是参数/特征变换；MLA 压缩的是注意力的逐 token 记忆表征。这二者是正交的。MoE 降低的是激活的 FFN 计算量；MLA 降低的是 KV-cache 的宽度。两个都需要，因为 LLM 的成本不是一维的。

DeepSeek-V3 紧接着问了一个问题：这个高效架构能不能撑到前沿通用模型的规模？它保留了 MLA 和 DeepSeekMoE，但加入了无辅助损失的负载均衡、多 token 预测，以及大规模的 FP8/系统工程。到这个阶段，DeepSeek 不再是发明某一个数学 trick；它是在证明，在隐/参数轴上和 KV-cache 轴上的优化，经得起前沿规模训练的考验。

![小黑把笨重 KV 背包压缩成可服务的小胶囊](/books/mlsys/assets/deepseek-roadmap-illustrations/04-mla-system-serving.png)

DeepSeek-R1 加上了第三个轴：推理轨迹长度。在 V3 之后，问题不再只是「模型能存多少知识？」或「以多低的成本做长上下文推理？」问题变成了：模型能不能在测试时投入更多计算并产出更好的结果？GRPO 把可验证的结果变成了强化信号，而且不需要 critic 模型。在这个框架下，R1 主要不是压缩隐维度或序列维度。它在优化轨迹维度：更长的推理链、更多的自我检查、更审慎的问题求解。但这立即使得一个新的系统瓶颈浮现：长推理链和 agentic workflow 会产生长上下文、高 KV-cache 压力，以及昂贵的 rollout。

这也就是为什么 DeepSeek-V4 是自然的下一步。MLA 压缩了每个 token 的 KV 宽度，但仍然为每个 token 存储一个缓存状态，所以缓存随序列长度线性增长。V4 从隐维度的 KV 压缩走向了序列维度的压缩，通过 CSA/HCA 来实现。CSA 把 token 块压缩并稀疏地选择相关的压缩块；HCA 压缩得更激进，并在高度压缩后的序列上做稠密注意力。V4 还引入了异构 KV-cache 管理、片上磁盘 KV 存储、mHC、Muon、FP4 QAT、OPD、rollout 基础设施和沙箱基础设施。

![小黑背着推理带走向百万上下文高塔](/books/mlsys/assets/deepseek-roadmap-illustrations/05-reasoning-long-context.png)

梳理之后的路线图如下：

- **DeepSeekMoE**：通过稀疏专家激活控制参数/隐容量。
- **DeepSeek-Coder / DeepSeekMath**：通过领域特定数据和目标函数塑造学到的特征基。
- **DeepSeek-V2**：通过 MLA 压缩逐 token 的 KV 记忆，同时通过 MoE 保持稀疏容量。
- **DeepSeek-V3**：通过负载均衡、MTP 和 FP8/系统优化，将这个经济型架构扩展到前沿通用模型。
- **DeepSeek-R1**：通过基于 GRPO 的强化学习扩展推理轨迹。
- **DeepSeek-V4**：通过 CSA/HCA 和全栈缓存/系统协同设计，控制由长推理和 agentic workflow 引起的序列/上下文爆炸。

压缩视角下的核心论点是简单的：DeepSeek 的路线图是一个在资源约束下做能力 scaling 的案例研究。随着模型能力增长，瓶颈从参数容量，转移到领域表征，再到 KV-cache 记忆，再到推理轨迹成本，最终到百万 token 级别的上下文系统。每一代 DeepSeek 瞄准的都是上一代暴露出来的最主要瓶颈。

下面的路线图按首次公开发表/发布日期排列，再按每项工作中引入或巩固的主要技术创新来组织。对 arXiv 论文，排序使用首次提交日期；修订日期仅在影响本地 PDF 时做标注。DeepSeek-V4 条目使用的是 Hugging Face 模型卡和技术报告，而非 arXiv 记录。

## 创新 1：DeepSeekMoE——让稀疏容量更有效

### 1. 要解决的问题

稠密 scaling 贵，因为每个 token 都要激活整个模型。如果通过把稠密 Transformer 做得更大来增加模型容量，训练和推理成本都跟着激活参数数量正比增长。MoE 提供了一种天然的方式来解耦总参数和激活参数：模型可以包含很多专家，但每个 token 只激活其中的一小部分。

然而，传统的 top-$K$ MoE 有一个重要的弱点：稀疏激活并不自动意味着干净的专业化。如果每个路由专家都又大又粗粒度，单个专家可能仍然要表征很多不相关的知识类型。这样的专家就变成了混杂型的「迷你稠密模型」，而不是干净的专业选手。与此同时，公共知识——基础句法、高频 token 模式、常见语义结构、通用语言建模能力——可能在很多路由专家中被冗余学习。这把稀疏容量的有效价值给削弱了。

### 2. 核心技术思路

DeepSeekMoE 改进 MoE 的方式不是简单地加更多专家，而是改变专家专业化的结构。它引入了两个耦合的思路：细粒度专家切分和共享专家隔离。

**细粒度专家切分**提高路由的分辨率。与其选几个大专家，不如创建很多小专家，让路由器为每个 token 组合出更精确的专家集合。概念上的转变是从「选少数宽泛的专家」变成了「为每个 token 组合出更精细的子技能」。

**共享专家隔离**为公共知识引入了始终激活的共享专家。概念上的转变是把公共容量跟路由容量分开。共享专家为几乎所有 token 都需要的知识提供稳定通路，而路由专家则相对被鼓励专注于残差型、专用型或长尾型的模式。

![DeepSeekMoE: 从粗粒度路由到细粒度专家再到共享专家](/books/mlsys/assets/deepseek_moe_clean_diagram.png)

### 3. 详细技术实现

在传统 MoE 层中，假设模型有 $N$ 个路由专家，每个 token 激活 $K$ 个专家。每个专家通常是一个全尺寸的 FFN，所以路由器是在少量宽泛的变换中做选择。DeepSeekMoE 通过拆分 FFN 中间维度改变了这一点。如果把每个传统专家切分成 $m$ 个更小的专家，专家池就从 $N$ 个增长到 $mN$ 个，每个专家大约是原始中间宽度的 $1/m$。路由器则激活 $mK$ 个更小的专家，使得激活专家宽度和逐 token 的 FFN 计算量大致与原始 top-$K$ 设计相当。

于是前向传播是三项之和：残差/token 输入、共享专家的输出，以及被选中路由专家的门控输出。对于路由专家，路由器计算 token 到专家的亲和度分数，只保留 top-$K_r$ 个路由专家，规范化选中的门值，再把每个选中专家的输出乘以它的门值。一个重要的实现细节是，「更多专家」并不比例地意味着「更多激活计算」。以论文中的 2B 验证模型为例，它用了一个共享专家和 63 个路由专家，每个 token 激活七个路由专家；每个专家是标准 FFN 的 0.25 倍大小。

用简化符号，MoE 的输出可以写成：

\[h'_t =
u_t
+
\sum_{i=1}^{N_s} \operatorname{FFN}^{(s)}_i(u_t)
+
\sum_{i=1}^{N_r} g_{i,t}\operatorname{FFN}^{(r)}_i(u_t),\]

其中 $N_s$ 个共享专家始终激活，$N_r$ 个路由专家构成候选池，$g_{i,t}$ 仅对 token $t$ 选中的 top-$K_r$ 个路由专家非零。这个方程就是共享容量和路由容量之间的实际区别：共享专家贡献稠密的公共通路；路由专家贡献稀疏的逐 token 专用容量。

共享专家隔离是通过把一部分专家完全从路由器中剔除来实现的。这些共享专家对每个 token 都是确定性激活的。为了保持总计算量不变，当加入共享专家时，激活的路由专家数量相应减少。所以完整的 DeepSeekMoE 层并不是对所有专家做简单的 top-$K$；而是「永远用共享专家，然后在路由专家上做路由」。在 16B 的缩放模型中，每个 MoE 层使用两个共享专家和 64 个路由专家，每个 token 路由到六个路由专家，每个专家保持标准 FFN 的 0.25 倍大小。在初步的 145B 设定中，论文报告了四个共享专家和 128 个路由专家，激活十二个路由专家，每个专家为标准 FFN 的 0.125 倍大小。

论文还加入了负载均衡机制，因为细粒度路由增加了专家崩溃的风险。它使用了专家级均衡损失来防止少数路由专家接收大部分 token。当专家分布在多个设备上时，还使用了设备级均衡损失，这样专家并行就不会产生严重的硬件不均衡。对于 16B 模型，专家级均衡因子被设得非常小，因为在它们的并行化策略下，更强的均衡反而降低了性能。

训练和验证是分阶段进行的。论文首先在 2B 规模的模型上测试，把所有 FFN 都替换成 MoE 层，然后将 DeepSeekMoE 与 Hash Layer、Switch Transformer、GShard、更大的 GShard 变体以及稠密上界基线做对比。然后它在 2T token 上训练 DeepSeekMoE 16B，再执行 SFT 得到对话模型。消融实验也是实现叙事的一部分：它们分别测试了共享专家隔离、将专家切分到 32 或 64 个的更细粒度、不同共享/路由比例、禁用 top 路由专家、以及减少激活专家数量。正是这些实验支撑了架构层面的论断：DeepSeekMoE 提高的是专业化水平，而不仅仅是增加参数数量。

### 4. 为什么这项技术能起作用

细粒度专家切分之所以能起作用，是因为许多 token 级别的计算是组合性的。一个 token 很少只需要某一种又大又单一的能力。它可能同时需要句法、局部语义、事实回忆、代码结构、数学模式识别、多语言知识，或者领域特定的术语。粗粒度的大专家强迫这些技能被捆绑在一起。更小的专家则让路由器能够组合出一组更精确的子能力。

结果是更高的有效 MoE 表达能力。即使总激活计算量差不多，可能的专家组合数量却大幅增加。模型有更多的方式来表征不同类型的 token、领域和上下文。好处不仅仅是更多参数；而是更高的路由分辨率。

共享专家隔离之所以能起作用，是因为公共特征是统计上高频的。共享专家对所有 token 都激活，所以它们从整个训练分布中接收到稠密且一致的梯度。路由专家只从路由到它们的 token 子集中接收梯度。因为公共语言模式到处出现，共享专家天然处于更可靠地学习这些模式的位置。

一旦共享专家学到了公共结构的一部分，路由专家就可以被更经济地使用。它们不再承受独立重新学习每一个基础语言学或语义模式的压力。它们最有价值的贡献反而是去解释那些公共通路已经解释得不太好的部分：领域特定的、罕见的、依赖 token 的、或者依赖上下文的残差模式。

### 5. 为什么这项技术有局限

DeepSeekMoE 并没有提供硬的知识解耦。这是关键的限制条件。如果一个路由专家对某个 token 是激活的，它就会收到来自完整 token 级损失的梯度。损失并不会被分解成「公共特征损失」和「专用特征损失」。公共特征梯度仍然可以更新路由专家，路由专家仍然可以学习公共知识。

共享专家只创造了一个架构先验。它们并不强迫公共知识留在路由专家之外。如果路由器反复把通用 token 发给某些路由专家，那些专家仍然可能变得通用。如果重复的公共特征能够降低损失，优化过程仍然可能会保留冗余。

细粒度专家也引入了系统和优化上的挑战。更多专家意味着更多路由决策、更多调度复杂度，以及潜在的更难的负载均衡。如果路由坍塌，某些专家可能被过度使用，而另一些则训练不足。如果专家太细粒度，单个专家可能缺乏足够的容量或数据来学到稳健的函数。细粒度切分提高了路由分辨率，但也使路由质量变得更加重要。

**核心局限。**DeepSeekMoE 提高了稀疏容量的可用性，但它并不能保证干净的专家解耦、完美的负载均衡，也无法消除共享专家和路由专家之间的冗余。

### 6. 过渡到下一个瓶颈

DeepSeekMoE 让稀疏容量变得更有用，但它仍然是领域无关的。下一个瓶颈不是如何把通用 token 路由给专家；而是如何让训练分布暴露出困难领域的结构。这就是 DeepSeek-Coder 把路线图从纯架构效率转向数据/目标函数设计的转折点。

## 创新 2：DeepSeek-Coder——仓库级代码智能

### 1. 要解决的问题

DeepSeek-Coder 解决的是 DeepSeek 路线图中第一个主要的领域专业化瓶颈：一个通用语言模型不会仅仅因为 scale 了参数就自动变成强大的代码模型。代码在结构上与自然语言不同。它有严格的语法、可执行的语义、长程依赖、API、测试、构建系统、文件级组织和仓库级约定。一个主要在普通文本或孤立的代码片段上训练的模型，可能学到局部句法和常见编程范式，但在跨文件依赖、代码填空、仓库级上下文，以及真实的软件编辑任务上会感到吃力。

核心问题不是简单的「生成代码」。而是：一个开源模型怎样才能把代码当作一个软件系统对象来学习，而不是当作一串不连贯的 token 序列？DeepSeek-Coder 的回答是，把训练单元向真实软件仓库靠拢，并把目标函数与程序员实际编辑代码的方式对齐。论文推出了从 1.3B 到 33B 参数的模型，从零开始在 2T token 上训练，使用高质量的项目级代码语料、填空式/FIM 式训练，以及 16K 上下文窗口。

### 2. 核心技术思路

核心思路是：代码智能在成为 agent 问题之前，先是一个数据和上下文问题。DeepSeek-Coder 不只是在一个通用模型上做代码指令微调。它通过大规模项目级预训练，把代码能力建进了基座模型里。仓库级数据让模型暴露在软件的自然结构中：定义、import、依赖、测试、注释、文件布局，以及反复出现的命名约定。

第二个思路是让学习目标更接近真实的代码编辑场景。程序员很少只是从左到右地追加文本。他们经常在已有文件中插入、替换或补全代码。DeepSeek-Coder 使用填空式（fill-in-the-middle / fill-in-the-blank）训练，使模型能够在给定前缀和后缀的条件下生成缺失的代码段。这对 IDE 补全、打补丁和局部重构至关重要。

第三个思路是扩展上下文。代码的长程依赖通常比自然语言更强。一个符号、函数签名、import 或测试，即便在几百几千个 token 之外，也可能决定正确的补全。16K 上下文窗口使仓库级训练更有意义，因为模型可以在预训练期间观察到更大的软件单元。

### 3. 详细技术实现

DeepSeek-Coder 是从零开始在 2T token 上训练的，而不是从通用对话模型改编而来。语料混合以代码为主：87% 源代码，10% 与代码相关的英文自然语言（来自 GitHub Markdown 和 StackExchange 等来源），3% 与代码无关的中文自然语言。源代码侧覆盖 87 种编程语言。经过清洗后，论文报告大约 798GB 源代码，约 6.03 亿个文件。

数据流水线是实现中的重要部分。DeepSeek 收集了 2023 年 2 月之前创建的公开 GitHub 仓库，然后应用了与 StarCoder 类似的基于规则的过滤器：去掉平均行长度超过 100 字符、最大行长度超过 1000 字符、字母字符少于 25%、大多数语言中的 XML 类样板代码、HTML 中可见文本比例过低的文件，以及超出 50 到 5000 字符范围的数据密集型 JSON/YAML。这些过滤器在后续筛选之前，把初始数据缩减到了原始规模的 32.8%。

仓库级构造是通过依赖解析实现的。对于每个项目，流水线使用语言特定的正则表达式提取跨文件调用模式，例如 Python 的 `import`、C# 的 `using`、C 的 `include`。它构建文件依赖图，分解不连通的子图，并应用一种改进的拓扑排序，选择入度最小的文件，使得在存在环的情况下仍能继续推进。排序后的文件被拼接成仓库级训练样本，并在每个文件开头插入文件路径注释，让模型看到位置信息。这比「在仓库上训练」要具体得多：序列顺序是被精心安排过的，依赖项倾向于出现在依赖它们的文件之前。

去重也是仓库感知的。论文不按单个文件去重，而是把拼接后的仓库级代码当成一个样本，并在这个级别做近似去重，从而避免了按文件去重会删除个别文件、破坏仓库结构的失败模式。后续的质量筛选阶段结合了编译器检查、质量模型和启发式规则，来删除含有语法错误、可读性差或模块性弱的代码。

训练目标结合了普通的 next-token 预测和 Fill-in-the-Middle。FIM 随机把文本切分为前缀、中间和后缀，然后训练模型从前后文中重建中间部分。论文研究了 PSM 和 SPM 两种变体，并对 FIM 比例做了消融。它发现 100% FIM 在 HumanEval-FIM 上得分最好，但会损害普通补全，于是 50% FIM 成为实际权衡。最终模型系列使用 16K 上下文窗口，使仓库级打包和代码填空在预训练中真正暴露了长跨文件上下文。发布系列覆盖 1.3B、5.7B、6.7B 和 33B base/instruct 变体，在基座预训练后追加了指令微调。

一个重要的实践细节是，FIM 不只是评估时的特性。它在打包之前就改变了预训练样本：一份代码文档被切成 prefix、middle 和 suffix 段，控制 token 标记空缺位置，而目标序列把缺失的 middle 放在前后文之后。这让填空成为基座模型的原生行为，而不是仅在指令微调阶段才学会的行为。

### 4. 为什么这项技术能起作用

DeepSeek-Coder 之所以起作用，是因为它缩小了训练分布与编程真实结构之间的错配。如果一个模型在仓库级数据上训练，它会反复观察到软件作为一个连接的系统，而不是孤立的局部句法。经过大量样本，它可以学到诸如 import-使用关系、类-方法组织、测试驱动行为、库约定和 API 使用模式等规律。

FIM 起作用是因为代码编辑天然是双向的。一个缺失的实现不仅受到它之前的代码约束，也受到它之后的代码约束。例如，后缀可能揭示出期望的返回类型、错误处理、变量名或下游使用方式。通过训练模型利用两侧信息来填补缺失段，DeepSeek-Coder 教给它的是一种与实际编码方式相匹配的编辑行为。

长上下文起作用是因为代码具有高长程互信息。在自然语言中，远处的上下文可能有用但常常是可选的。在代码中，远处的上下文可能是决定性的。一个 import 别名、一个类型定义、或者一条测试断言，都可能决定模型应该生成什么。更长的上下文窗口直接提升了模型利用软件结构的能力。

所以 DeepSeek-Coder 的成功源于把数据单元、目标函数和上下文长度与代码的结构对齐了。这才是真正的贡献。不只是「更多的代码数据」；而是一种更代码原生的预训练范式。

### 5. 为什么这项技术有局限

DeepSeek-Coder 的主要局限是它本质上仍是一个静态代码模型，而不是一个可执行的软件工程 agent。它从仓库级代码数据中学习，但它并不会通过定义真正编程的那个循环来原生地学习：编辑代码、跑测试、观察失败、检查错误、修正补丁、重复。这个差距在后来出现的可执行编码基准测试和仓库 agent 工作中变得更加清晰，那些工作评估模型的环境要求代码必须被检查、修改、运行和修复，而不仅仅是预测。

长上下文也不等于长周期软件工程。真实任务需要仓库探索、多文件规划、测试执行、故障诊断和迭代补丁优化。[SWE-QA-Pro](https://arxiv.org/abs/2603.16124) 报告了在长尾仓库上使用 agentic workflow 带来的显著增益，而 [FeatureBench](https://arxiv.org/abs/2602.10975) 显示，即使是强大的 agentic 系统，面向功能的开发仍然很困难。这些结果从不同角度说明同一个事实：仓库级预训练帮助模型理解软件结构，但它本身并不能创造一个完整的开发循环。

后来的其他基准测试也进一步刻画了剩余的差距。[C3-Bench](https://arxiv.org/abs/2601.15879) 强调指令控制的补全，[RepoZero](https://arxiv.org/abs/2605.07122) 测试完整的仓库复现，[SWE-Bench Mobile](https://arxiv.org/abs/2602.09540) 引入了工业级移动开发的约束，如 PRD、Figma 设计、Swift/Objective-C 代码库和平台测试。它们共同表明，代码智能最终必须变得工具落地、指令跟随、多模态且执行感知。

**核心局限。**DeepSeek-Coder 解决的是代码表征学习，而非软件工程 agency。它改进了模型对代码仓库的建模能力，但并没有完全解决可执行反馈、长周期规划、多文件干预、指令控制编辑、仓库合成、多模态产品落地或 agent/工具编排等问题。

### 6. 过渡到下一个瓶颈

DeepSeek-Coder 表明，数据布局和训练目标可以产生领域能力，但它的代码能力主要还是预测性的：补全、填空、生成。DeepSeekMath 把同样的模式带进了一个最终答案往往可验证的领域，这使得在领域预训练之上叠加强化学习成为可能。

## 创新 3：DeepSeekMath——从代码智能到数学推理

### 1. 要解决的问题

DeepSeekMath 解决的是跟 DeepSeek-Coder 不同的瓶颈。代码预训练给模型带来了语法、过程化结构和算法模式，但数学推理需要一些更特定的东西：在多步间维持符号约束、正确转换表达式、选择合适的中间引理，并通过一条有效的推理链达到答案。问题不仅在于模型缺少数学事实；更深层的问题是，普通的 next-token 预测并不强力地强制推理正确性。

在 DeepSeekMath 之前，很多开源模型可以模仿解答风格，但在竞赛级别的数学上仍然不行。它们生成的推理可能看起来合理，但微小的局部错误就足以让最终答案无效。DeepSeekMath 瞄准的是一个精准的能力 scaling 障碍：一个开源 7B 规模的模型怎样才能获得强大的数学推理能力，而不依赖庞大的闭源模型规模、外部符号工具或昂贵的人工标注推理链？DeepSeekMath 的回答是把数学聚焦的继续预训练与强化学习结合起来，具体而言就是 GRPO。论文在 DeepSeek-Coder-Base-v1.5 7B 的基础上继续训练了 120B 来自 Common Crawl 的数学相关 token，混合自然语言和代码数据，在不使用外部工具包或投票的情况下，在 MATH 上达到 51.7%，使用 64 样本自一致性达到 60.9%。

### 2. 核心技术思路

核心思路是，数学推理的提升可以通过对齐数据、基础能力和 RL 目标来实现。

**第一个组件**是数学特定的数据构造。DeepSeekMath 并不仅仅依赖现有的精选数学数据集，这些数据集规模太小，撑不起广泛的预训练。它改为从 web-scale 的 Common Crawl 中挖掘数学相关数据，使用了一个精心设计的数据选择流水线。模型需要不仅接触到最终答案，还要接触到数学语言、推导、符号记法、类证明的解释和问题求解模式。

**第二个组件**是从具备代码能力的基座模型出发。DeepSeekMath 从 DeepSeek-Coder-Base-v1.5 7B 继续训练，而不是从通用自然语言模型出发。这是一个合理的设计选择，因为代码预训练已经给模型带来了过程化和符号化的规律：函数、变量、控制流、精确语法和算法分解。这些跟数学不完全相同，但它们提供了一个比纯文本更好的数学推理基底。

**第三个组件**是 GRPO，一种轻量级的强化学习方法。与标准 PPO 使用单独的 critic/value 模型不同，GRPO 在一组采样回答中估算相对优势。这降低了 PPO 的内存开销，同时仍然推动模型向答案正确性前进。策略上的动机很清晰：利用可以验证结果的数学题，把推理改进变成一个可扩展的 RL 问题。

### 3. 详细技术实现

DeepSeekMath 的起点是数据构造，而不是 RL。论文从 Common Crawl 使用迭代的 fastText 流水线构建了 DeepSeekMath Corpus。它先以 OpenWebMath 作为高质量种子语料，从中采样 50 万个正例和从 Common Crawl 中采样 50 万个负例，训练一个 fastText 分类器，向量维度 256，学习率 0.1，词 n-gram 长度上限 3，最小词数 3，训练 3 个 epoch。Common Crawl 先按 URL 去重并近似去重到约 400 亿 HTML 页面，然后由分类器打分。

数据挖掘循环不是做一次，而是反复迭代。第一轮之后，DeepSeek 把 Common Crawl 按域名组织，找出其中超过 10% 页面被收集为数学相关的域名，人工标注这些域名中的数学 URL 路径，再把这些页面加回到正例种子池中。经过四轮迭代，流水线产出了 3550 万个数学网页、120B token。语料是多语的，主要为英文和中文，基准测试的污染通过移除含有评测基准精确 10-gram 匹配的网页来过滤，对较短的基准字符串（3 到 9 gram）做精确匹配。

模型训练有两个不同的规模。首先，论文使用 1.3B 模型在不同数学语料上训练 150B token 来验证语料质量。这些实验使用 AdamW，$\beta_1=0.9$、$\beta_2=0.95$，weight decay 0.1，多步学习率调度，2000 步 warmup，峰值学习率 $5.3 \times 10^{-4}$，batch size 4M token，4K 上下文。主要的 DeepSeekMath-Base 7B 则从 DeepSeek-Coder-Base-v1.5 7B 初始化，训练 500B token，混合 56% DeepSeekMath Corpus、4% AlgebraicStack、10% arXiv、20% GitHub 代码、10% 中英文自然语言 Common Crawl。在 7B 训练中，峰值学习率为 $4.2 \times 10^{-4}$，batch size 为 10M token。

继续预训练之后，DeepSeekMath 应用了数学指令微调。指令阶段混合了思维链、程序化思维和工具集成推理数据，这样模型就能学会多种作答风格：自包含的自然语言解答、Python 辅助解答和工具集成解答。这也是论文同时评估无工具数学解题和带 Python 辅助的数学解题的原因。

RL 阶段引入了 GRPO。对每个 prompt，GRPO 采样一组输出，给它们打分，再把每个输出的奖励相对组内均值和标准差进行规范化，来估算优势。这样就省掉了 PPO 中独立的 critic/value 模型。DeepSeekMath 只用了一部分英文指令微调数据来做 RL，但仍然报告了从 DeepSeekMath-Instruct 到 DeepSeekMath-RL 的性能提升。论文还把 GRPO 与相关方法如 RFT、DPO 和 PPO 做了比较，研究了在线 vs 离线采样、结果监督 vs 过程监督，以及迭代式 RL。所以实现不是简单的「加 RL」；而是一整套数据挖掘流水线、继续预训练配方、指令微调阶段以及无 critic 的组相对 RL 配方。

GRPO 的优势估计是节省内存的核心操作：

\[A_i =
\frac{r_i - \operatorname{mean}(r_1,\ldots,r_G)}
{\operatorname{std}(r_1,\ldots,r_G)}.\]

PPO 需要一个学习出来的 value 模型来估计优势；GRPO 则利用采样组内的奖励分布。这就是为什么这个方法对 7B 规模的数学 RL 有吸引力，也为什么后来被用到更大的 DeepSeek 推理模型中。

### 4. 为什么这项技术能起作用

DeepSeekMath 之所以能起作用，是因为数学有一个有用的特性：很多问题是结果可验证的。与开放式的写作不同，数学问题常常有清楚的最终答案。这让强化学习变得更可行。模型可以采样多条推理路径，正确的输出为哪些路径应该被强化提供了信号。

这一方法也之所以起作用，还因为代码预训练和数学推理共享了一些结构特征。两者都需要变量、符号操作、长程一致性和过程分解。一个在代码上训练过的基座模型，天然比纯自然语言模型更善于表征逐步的变换。继续的数学预训练则把这个过程化基底向数学记法和求解模式的方向转移。

GRPO 作为一种务实的妥协而起作用。它不是一个完整的过程验证器，但它通过避免单独训练一个 critic 模型使 RL 更具可扩展性。对 7B 模型来说，这一点很重要：这一方法在提升推理能力的同时，不需要承担大规模 PPO RL 的完整成本结构。从这个意义上讲，DeepSeekMath 不只是一个数学模型；它同时也是对低成本推理放大的一次实验。

自一致性结果也揭示了模型学到了有用的推理分布，而不仅仅是单一确定性映射。当模型采样多个解答并投票或从中选择时，性能大幅提升，这表明即便单次采样可能失败，模型分布中仍然存在正确的推理路径。DeepSeekMath 报告在不使用外部工具包或投票的情况下 MATH 上达到 51.7%，使用 64 样本自一致性则达到 60.9%。

### 5. 为什么这项技术有局限

DeepSeekMath 的主要局限是，它的数学推理优化很大程度上依靠最终答案的正确性，而不是严格的证明验证。正确的最终答案并不保证推导正确。推理链中可能包含幸运猜测、无效步骤、隐含的抵消或者不一致的论证。这个局限在后续工作中变得明确：[DeepSeekMath-V2](https://arxiv.org/abs/2511.22570) 指出，仅靠最终答案奖励的 RL 可以驱动强基准测试的提升，但仍然不能保证逐步正确性。

奖励信号最多只能跟验证器一样好。很多数学问题，如果答案是数字或表达式就很容易检查，但如果任务要求给出证明、构造或解释，就很难检查。对于证明导向的数学，仅靠最终答案奖励是不够的。[DeepSeek-Prover-V2](https://arxiv.org/abs/2504.21801) 后来转向了基于 Lean 的形式化定理证明和子目标分解，表明数学推理最终需要形式化验证，而不仅仅是用自然语言匹配答案。

DeepSeekMath 也缺乏显式过程监督和长周期证明搜索。[Qwen2.5-Math](https://arxiv.org/abs/2409.12122) 走向迭代式验证器/模型协同进化；[Kimi k1.5](https://arxiv.org/abs/2501.12599) 将长上下文 RL 作为新的 scaling 轴；Google DeepMind 的 [AlphaProof 和 AlphaGeometry 2](https://deepmind.google/discover/blog/ai-solves-imo-problems-at-silver-medal-level/) 展示了将语言模型与形式化或符号化系统结合的价值。DeepSeekMath 在作为一个非形式化的数学推理器方面是广泛有用的，但它不是一个证明系统，也不是一个自动化的数学发现引擎。

**核心局限。**DeepSeekMath 把数学推理变成了一个可扩展的数据加 RL 问题，但它并没有解决忠实的证明推理、过程验证、形式化正确性、长周期证明搜索或自动化数学发现。

### 6. 过渡到下一个瓶颈

DeepSeekMath 为可验证推理添加了一个廉价的 RL 机制，但它仍然是一个 7B 的领域模型。下一个瓶颈是架构层面的：如何在一个足够大的通用模型中结合稀疏容量和廉价的长上下文推理，以支撑代码、数学和广泛指令跟随。DeepSeek-V2 就是这个融合点。

## 创新 4：DeepSeek-V2——将稀疏容量与廉价长上下文推理相结合

### 1. 要解决的问题

DeepSeek-V2 解决的是 DeepSeekMoE、DeepSeek-Coder 和 DeepSeekMath 之后的下一个瓶颈：如何让一个强大的通用模型在训练时和推理时都是经济的。

DeepSeekMoE 已经展示了如何在不对每个 token 激活全部参数的情况下增加总参数容量。但仅靠稀疏容量还不能解决推理成本问题。在自回归解码中，成本的很大一部分来自注意力的 KV cache。即使每个 token 只激活一部分 MoE 专家，模型仍然需要为长上下文生成存储和读取历史的 key/value 状态。随着上下文增长，KV cache 变成内存容量和内存带宽的瓶颈。

到这里路线图出现了转折：容量的 scaling 不仅受 FLOPs 制约；也受内存搬运和 KV-cache 存储的制约。DeepSeek-V2 同时瞄准了两个成本：通过 DeepSeekMoE 得到稀疏计算，通过多头隐注意力（MLA）得到廉价的长上下文推理。论文将 DeepSeek-V2 描述为一个总参数 236B、每 token 仅激活 21B 的 MoE 模型，支持 128K 上下文，与 DeepSeek 67B 相比训练成本降低 42.5%、KV-cache 减少 93.3%、最大生成吞吐量最高提升 5.76 倍。

### 2. 核心技术思路

DeepSeek-V2 的核心思路是把稀疏容量和压缩的注意力状态结合起来。

DeepSeekMoE 解决了激活参数的问题：模型可以有巨大的总参数量，但每个 token 只用一小部分专家。MLA 解决了 KV-cache 的问题：与其为每个注意力头存储巨大的 key/value 张量，不如把 KV 状态压缩成隐表征。这两种机制加在一起，让 DeepSeek-V2 在经济性上达到了单独靠任何一方都无法实现的程度。

从概念上讲，DeepSeek-V2 是 DeepSeek 从「把模型变大但稀疏」转向「把模型变大、稀疏且可服务」的那个节点。这让 V2 成为决定性的架构里程碑。它不仅是一个更好的模型；它是一个围绕着推理经济性来设计的模型。

### 3. 详细技术实现

DeepSeek-V2 是一个 Transformer，它的注意力和 FFN 模块都重新设计了。发布的完整模型有 236B 总参数，每 token 激活 21B；较小的 V2-Lite 有 15.7B 总参数，每 token 激活 2.4B。在 FFN 模块中，V2 采用了 DeepSeekMoE：共享专家始终激活，路由专家通过 top-$K$ 路由选择，训练中使用专家并行。因为 MoE 路由产生了通信压力，V2 增加了设备受限路由，使得一个 token 选中的路由专家被约束在有限数量的设备上。它还使用了专家级和设备级的辅助均衡损失，以及当不均衡超出容量时的 token 丢弃策略。

注意力实现的独特之处在于 MLA。在标准 MHA 中，生成为每个之前 token 和每一层缓存所有 key 和 value，每个 token 需要缓存 $2n_h d_h l$ 个元素，其中 $n_h$ 是头的数量，$d_h$ 是每头维度，$l$ 是层数。MLA 改为计算一个压缩的隐 KV 向量：

\[c^{KV}_t = W^{DKV} h_t\]

并通过上投影重建压缩的 key 和 value：

\[k^C_t = W^{UK} c^{KV}_t,\quad v^C_t = W^{UV} c^{KV}_t.\]

在推理时，模型缓存的是 $c^{KV}_t$ 而不是完整的每头 key 和 value。论文指出 $W^{UK}$ 可以在推理时被吸收进 query 投影，而 $W^{UV}$ 可以被吸收进输出投影，所以模型不需要为每个缓存的前缀 token 显式物化完整的 key 和 value。

MLA 还加入了低秩 query 压缩以减少训练时的激活内存：

\[c^Q_t = W^{DQ}h_t,\quad q^C_t = W^{UQ}c^Q_t.\]

一个微妙的实现问题是 RoPE。如果 RoPE 直接应用到压缩后的 key 上，位置敏感的旋转会阻止 key 上投影在推理时被吸收进 query 侧。V2 用解耦的 RoPE 解决了这个问题：内容 key/query 走压缩路径，而单独携带 RoPE 的 query/key 组件被生产出来，并与压缩组件做拼接。这样一来，V2 同时缓存隐 KV 向量和解耦的 RoPE key，缓存大小正比于 $(d_c + d^R_h)l$ 而非完整 MHA 的 $2n_h d_h l$。

预训练和对齐配方也是清楚的。V2 在 8.1T token 的多源语料上预训练，然后扩展到 128K 上下文，再用 150 万条涵盖数学、代码、写作、推理、安全等领域的对话做对齐。监督微调产出了对话模型，GRPO 式强化学习进一步将模型与人类偏好对齐。标题中的效率结果——训练成本降 42.5%、KV-cache 降 93.3%、最大生成吞吐量最高 5.76 倍于 DeepSeek 67B——都来自这个 MoE 加 MLA 的联合实现，而不是仅靠 MoE。

### 4. 为什么这项技术能起作用

DeepSeek-V2 之所以能起作用，是因为它攻击的是两个互相放大的不同 scaling 瓶颈。

第一个瓶颈是激活计算。稠密模型为所有 token 在所有参数上花费计算。DeepSeekMoE 通过使 FFN 计算条件化来降低这个成本：只有选中的专家才会被每个 token 激活。这让模型拥有高总容量而不随之产生成比例的逐 token FLOPs。

第二个瓶颈是注意力内存。在长上下文解码中，模型反复读取历史 KV 状态。即使 FFN 是稀疏的，注意力仍然可能被内存带宽卡住。MLA 通过把 KV cache 压缩成隐向量来减小这段历史状态的大小。这减少了 HBM 占用和内存带宽压力。

这个组合之所以强大，在于它对准了 LLM 真实的推理成本结构。MoE 降低了参数上的计算支出。MLA 降低了历史上的内存支出。模型在两条主要推理轴上同时变得更便宜：激活参数计算和 KV-cache 存储。

MLA 特别重要，因为解码性能往往受内存带宽而非纯计算制约。如果 KV cache 更小，每个生成的 token 需要加载的历史状态就更少。这可以提高吞吐量和批量容量。这就是为什么后续工作把 MLA 不是仅仅当作一种注意力变体，而是当做一种硬件相关的设计：它改变了注意力如何映射到加速器的内存系统上。

### 5. 为什么这项技术有局限

DeepSeek-V2 是重要的一步，但它并没有完全解决长上下文智能的问题。MLA 压缩的是 KV cache 的宽度，而不是序列长度。缓存小了很多，但它仍然随 token 数量增长。这就是为什么 V4 后来超越了 MLA，走向了混合 CSA/HCA 注意力：缓存宽度的压缩让 128K 上下文更便宜，但百万 token 上下文还需要沿着序列维度进行压缩或选择。

MLA 也是一种有损的架构压缩，伴随着实现上的取舍。它假设历史的注意力状态可以被紧凑地表征在隐空间中，这在很多时候是高效的，但对于需要精确检索、复制或超长程推理的场景，可能会丢失细粒度信息。它改变的是硬件平衡，而不是完全消除成本：最佳的执行策略取决于具体的加速器架构、重计算选择和推理条件。

最后，V2 也没有完全解决整个 MoE 系统的 scaling 问题。后来的 V3 仍然需要通过无辅助损失的负载均衡、MTP 和系统级训练优化来改进专家均衡、训练效率和前沿级稳定性。V2 减少了 KV cache，但长上下文推理仍然需要缓存复用、内存层级、稀疏执行和精心的 kernel/运行时协同设计。

**核心局限。**DeepSeek-V2 通过 MLA 大幅降低了长上下文推理成本，但还没有解决百万 token 上下文、稀疏长程检索、完整的缓存层级管理，或者前沿级长周期推理所需的训练系统问题。

### 6. 过渡到下一个瓶颈

V2 提供了经济的通用骨干：通过 DeepSeekMoE 实现稀疏 FFN，通过 MLA 实现压缩 KV 宽度。一旦这个骨干到位，路线图就分裂为两个直接的问题：同样的基底能否再次被代码专用化？以及它能否被 scale 成前沿通用模型？Coder-V2 回答了第一个；V3 回答了第二个。

## 创新 5：DeepSeek-Coder-V2——在 V2 骨干上做领域专用化

### 1. 要解决的问题

DeepSeek-Coder-V2 解决的是 DeepSeek-V2 之后出现的瓶颈：一个高效的通用模型并不会自动成为前沿代码模型。V2 提供了经济的 MoE + MLA 骨干，但代码智能有其自身的能力要求：仓库规模的上下文、大量编程语言、代码修复、补全、数学密集型编程、编译器反馈，以及长上下文项目理解。

问题是如何将一个强大的经济型通用模型专用化，同时不破坏它的通用能力。之前的 DeepSeek-Coder 是从零开始训练代码原生的表征。Coder-V2 问的是另一个问题：V2 架构能否通过改变语料混合、上下文长度、对齐数据和奖励信号，被继续训练成一个高端代码模型？

### 2. 核心技术思路

核心思路是在一个经济型通用骨干之上做领域专用化。DeepSeek-Coder-V2 不是独立的从零训练的代码模型，而是从一个中间阶段的 DeepSeek-V2 checkpoint 继续预训练而来。架构已经通过 DeepSeekMoE 具备了稀疏容量，通过 MLA 具备了高效的 KV-cache 处理。Coder-V2 改变的是这些容量被训练去表征什么。

训练混合是精心设计的：60% 源代码、10% 数学、30% 自然语言。代码提供了编程结构，数学保持了推理强度，自然语言则防止模型坍缩到狭窄的纯代码分布。对齐阶段则结合了代码、数学和通用指令数据，接着使用 GRPO 式强化学习，配上代码特定的奖励信号。

### 3. 详细技术实现

Coder-V2 继承了 V2 的 MoE 架构，包括高效的 MLA 加 DeepSeekMoE 骨干。然后它追加了 6T 的预训练 token，使得包括 V2 数据集在内的总 token 暴露量达到 10.2T。新的代码语料把语言支持从 86 种扩展到 338 种编程语言，并将 GitHub 源代码与代码相关的网页文本结合起来。它使用了与 DeepSeekMath 相同风格的迭代 Common Crawl 检索流水线来收集代码和数学页面。

数据流水线比通用代码爬取要具体得多。2023 年 11 月之前创建的公开 GitHub 仓库，用与 DeepSeek-Coder 相同的规则集和近似去重方法做了过滤。这产生了 821B 源代码 token，覆盖 338 种语言，以及 185B 代码相关文本 token，如 Markdown 和 issue。对于 Common Crawl，团队从编码论坛如 StackOverflow、库文档如 PyTorch docs、数学站点如 StackExchange 出发；使用 DeepSeek-V2 BPE tokenizer 训练 fastText 分类器；标注其中超过 10% 页面被收集为代码/数学相关的域名；标注匹配的 URL 路径；并重复检索循环。三轮迭代后，流水线收集到 70B 代码相关网页 token 和 221B 数学相关网页 token。一个类似的两轮迭代 GitHub 检索循环又添加了 94B 源代码 token，使新的代码语料达到 1,170B 代码相关 token（来自 GitHub 和 Common Crawl）。

训练混合是 60% 源代码、10% 数学和 30% 自然语言。自然语言从 DeepSeek-V2 训练数据中采样，这样模型在向代码专用化的同时，不会丢失通用指令和语言能力。训练从已经训练了 4.2T token 的中间 DeepSeek-V2 checkpoint 开始，再继续训练 6T token。论文报告了两个模型规模：DeepSeek-Coder-V2-Lite，16B 总参数/2.4B 激活参数；DeepSeek-Coder-V2，236B 总参数/21B 激活参数。

训练目标因模型大小而异。16B 模型同时使用 next-token 预测和 FIM，FIM 格式为 PSM——prefix、suffix 然后 middle，带有特殊 FIM 标记，在打包前以文档级应用，使用频率 0.5。236B 模型仅使用 next-token 预测。两者都遵循 DeepSeek-V2 风格的优化器：AdamW，$\beta_1=0.9$、$\beta_2=0.95$，weight decay 0.1，余弦学习率衰减，2000 步 warmup，衰减到初始学习率的 10%。论文还提到了一个稳定性调整：因为指数规范化导致了训练不稳定和梯度尖峰，实现中回退到了常规规范化。

上下文长度上升到 128K，使编码与仓库规模任务对齐。在对齐方面，Coder-V2 首先从代码、数学和通用指令数据构建了指令数据集。论文报告收集了 2 万条代码相关指令样本和 3 万条数学相关样本，然后用通用指令数据扩充。RL 使用与代码和数学相关的 prompt；每个代码 prompt 包含相应的测试用例。团队并非直接使用编译器通过/失败作为奖励，而是从编译器反馈中训练了一个奖励模型，因为很多 prompt 只有有限的测试，原始的 0/1 编译器信号可能稀疏或有误导性。GRPO 随后在这些代码/数学奖励信号上优化，不使用 critic，与 DeepSeek 更广泛的低成本 RL 偏好保持一致。

### 4. 为什么这项技术能起作用

Coder-V2 之所以能起作用，是因为它不在通用智能和代码专用化之间非此即彼。它从一个已经拥有高效容量的通用模型出发，然后通过继续预训练把这个容量偏向代码。这比从零重新训练一切更高效，也比浅层指令微调更不脆弱。

大规模代码语料改进了编程的表示基。数学语料帮助保持了算法和符号推理能力，这对竞赛编程和代码合成很重要。自然语言数据则保留了指令跟随、文档理解和通用对话能力。128K 上下文窗口使仓库规模和长文件编码更加现实。

RL 设置起作用是因为代码有不同寻常的有用反馈。测试、编译器和期望输出可以提供可验证的信号。但直接的编译器反馈可能稀疏或噪声大，所以从编译器产生的数据训练奖励模型可以给 GRPO 提供更平滑的指导。这延续了 DeepSeek 的模式：利用可验证的领域来创建更廉价的强化信号。

### 5. 为什么这项技术有局限

Coder-V2 仍然没有完全解决软件工程 agency 的问题。它改进了代码生成、补全、修复和推理，但它仍然更接近于一个强大的代码模型，而不是一个完整的开发 agent。真正的工程任务需要仓库探索、工具使用、多文件编辑、测试执行、故障诊断和迭代补丁优化。

它的奖励信号也受到测试质量的限制。如果测试不完整，通过了也并不保证正确性。一个从编译器/测试反馈训练出来的奖励模型可以比原始的通过/失败信号更好地泛化，但它仍然可能继承基准测试的伪影、覆盖率不足和奖励模型误差。

最后，Coder-V2 依赖于 V2 架构的长上下文和推理假设。MLA 让 128K 更经济，但它并没有解决百万 token 上下文、缓存层级或长周期 agent 轨迹的问题。这些瓶颈后来催生了 R1 的推理轨迹 scaling 和 V4 的长上下文系统重设计。

**核心局限。**DeepSeek-Coder-V2 证明了 V2 骨干可以被代码专用化，但它仍然没有把代码智能变成一个完全可执行、工具驱动、长周期的软件工程循环。

### 6. 过渡到下一个瓶颈

Coder-V2 证明了 V2 骨干可以承接一个大型的代码/数学继续训练阶段，而不会坍缩成一个狭窄的纯代码模型。剩下的问题是规模纪律：在数千亿参数的规模下，路由、通信、精度和训练稳定性变成了瓶颈。这就是 DeepSeek-V3 要应对的问题。

## 创新 6：DeepSeek-V3——把经济型架构扩展到前沿通用模型

### 1. 要解决的问题

DeepSeek-V3 解决的是跟 DeepSeek-V2 不同的瓶颈。V2 已经证明了 DeepSeekMoE + MLA 可以让大模型更经济：稀疏专家降低了激活的 FFN 计算，MLA 降低了 KV-cache 内存。但 V2 仍然不是最终的 scaling 答案。下一个问题是：这个高效架构能不能被扩展到前沿级通用模型，同时不丢失训练稳定性、负载均衡、推理效率和成本控制？

在 V3 的规模下，瓶颈不再是某一个单独的模块。它变成了一个耦合的 scaling 问题：模型有几千亿参数，每 token 只激活一小部分，专家路由必须保持均衡，通信开销必须被隐藏，低精度训练必须稳定，模型还必须从超大规模的语料中学到强大的通用、代码、数学和推理能力。DeepSeek-V3 是 DeepSeek 试图证明其高效架构不仅在中型规模上优雅，而且可以被 scale 到前沿能力的阶段。

论文报告的模型有 671B 总参数，每 token 激活 37B 参数。它使用 MLA 和 DeepSeekMoE，在 14.8T token 上预训练，技术报告声称性能可与领先闭源模型比肩，同时完整训练仅需 2.788M H800 GPU 小时。它还报告了一条稳定的训练曲线，没有不可恢复的 loss 尖峰或回滚。

### 2. 核心技术思路

DeepSeek-V3 的核心思路是成本有效的前沿 scaling。它并没有引入一个全新的模型系列。相反，它采用了 V2 中验证过的架构，通过一组有针对性的改进来做 scale：无辅助损失的负载均衡、多 token 预测、FP8 混合精度训练，以及广泛的分布式系统优化。

V3 的新颖之处不是「又是另一个 MoE 模型」。它真正的贡献在于证明了 V2 的设计可以被 scale 到一个大得多的通用模型，同时把训练成本和推理成本控制在合理范围。论文本身也说 V3 采用了 MLA 和 DeepSeekMoE 来自 V2，然后加入了无辅助损失的负载均衡和多 token 预测目标来获得更强的性能。

所以概念上的进展是：

V2 证明了高效架构；V3 证明了高效 scaling。

### 3. 详细技术实现

**第一根支柱**是前沿规模的 DeepSeekMoE。V3 有 671B 总参数，每 token 激活 37B 参数。它保留了 V2 的模式——MLA 做注意力，DeepSeekMoE 做 FFN，但改变了路由器。对每个 token，路由器计算 token 表征与每个路由专家质心之间的 sigmoid 亲和度分数，选择 top-$K_r$ 个专家，然后将选中的亲和度分数规范化为门值。共享专家仍然作为始终激活的 FFN 路径加入，路由专家的输出在被求和到模块输出之前，乘以它们的门值。

V3 关键的 MoE 实现变化是无辅助损失的负载均衡。V3 不通过一个大的辅助损失来强制负载均衡，而是给每个专家的亲和度分数加一个偏置项 $b_i$，只影响 top-$K$ 路由的选择。偏置影响哪些专家被选中，但最终的门值仍然来自原始亲和度分数。在每个训练步结束时，系统监控全 batch 的专家负载：如果某专家过载，其偏置以一个小步长 $\gamma$ 递减；如果欠载，则递增。这把负载均衡变成了一种路由控制机制，而不是一个与语言建模竞争的语义损失。V3 仍然保留了一个很小的互补序列级均衡损失，以避免在单个序列内出现极端不均衡。

路由的区分是微妙且重要的：

\[\text{选择使用 } s_{i,t}+b_i,
\qquad
\text{门控使用 } s_{i,t}.\]

偏置改变的是哪些专家对该 token 有资格被选中，但它并不直接缩放选中专家的输出。这尽可能地把均衡控制器排除在语义混合权重之外。

模型还使用了节点受限路由。在训练期间，每个 token 最多被发送到 $M$ 个节点，节点通过汇总各节点上最高专家亲和度的方式选出。这让跨节点的 MoE 通信保持有界。在这种均衡策略下，V3 报告训练和推理中均无 token 丢弃，这一点很重要，因为丢弃 token 是很多 MoE 系统中隐藏的质量和稳定性代价。

**第二根支柱**是 MLA，继承自 V2，但作为标准长上下文注意力模块使用。V3 缓存压缩的隐 KV 向量和解耦的 RoPE key，而非完整的每头 K/V 状态。Query 压缩也被用于减少训练时的激活内存。这就是使 128K 上下文与 671B 参数 MoE 模型共存成为可能的原因。

**第三根支柱**是多 token 预测（MTP）。V3 附加了顺序的 MTP 模块，用于预测 next token 之后的额外未来 token。每个 MTP 模块与主模型共享 embedding 层和输出头，将前一深度的 hidden state 与未来 token 的 embedding 拼接，投影拼接结果，跑一个 Transformer 模块，然后预测该深度对应的下一个未来 token。MTP 的损失跨深度取平均，乘以权重因子 $\lambda$ 后加到主目标中。在正常推理时，这些模块可以被丢弃，或者被改用作推测解码。

**第四根支柱**是训练系统。V3 在 2048 个 NVIDIA H800 GPU 上训练，每节点八块 GPU 通过 NVLink/NVSwitch 连接，节点间通过 InfiniBand 连接。训练框架使用 16 路流水线并行、跨八个节点的 64 路专家并行和 ZeRO-1 数据并行。DualPipe 从流水线两端调度前向和反向 chunk，并重叠注意力、all-to-all 分发、MLP 计算、all-to-all 合并和流水线通信。跨节点的 all-to-all kernel 与 MoE 路由器和集群拓扑协同设计：token 限制在最多四个目标节点，IB 和 NVLink 传输被重叠，仅保留约 20 个 SM 用于通信。

**第五根支柱**是内存和精度工程。V3 在反向传播时重计算 RMSNorm 和 MLA 上投影，以避免存储它们的激活值；在 CPU 上异步维护 EMA 参数；MTP 的 embedding/输出头与主模型在同一流水线 rank 上物理共享；使用 FP8 混合精度训练来降低内存并提高吞吐。预训练用了 14.8T token，随后两阶段上下文扩展——从 4K 式预训练到 32K 再到 128K，然后是 SFT 和 RL。报告中的 2.788M H800 GPU 小时训练成本，因此是模型架构加路由、精度、流水线、通信和内存协同设计的结果。

### 4. 为什么这项技术能起作用

V3 之所以能起作用，是因为它同时攻击了前沿 scaling 的主要成本来源。

DeepSeekMoE 降低了容量的成本。模型可以有 671B 总参数，但每个 token 只激活 37B。这意味着模型可以访问一个庞大的知识和变换池，而不用为每个 token 支付稠密模型的计算开销。

MLA 降低了长上下文推理的成本。没有 KV-cache 压缩，一个 128K 上下文的 MoE 模型仍然会面临严重的内存压力。MLA 降低了逐 token 的 KV-cache 宽度，使长上下文推理更加可行。

无辅助损失的均衡之所以能起作用，是因为 MoE 需要负载控制，但不一定需要通过与语言建模竞争的训练目标来实现。如果专家负载的修正通过路由偏置或类似机制——而非通过一个大的显式辅助损失——来处理，模型就可以在不扭曲主 next-token 学习信号的条件下保持利用率。核心思路是把负载均衡当作路由控制问题，而非语义目标。

MTP 之所以能起作用，是因为相对于语言中的结构量而言，next-token 预测的监督是稀疏的。预测多个未来 token 给模型提供了每条序列更多的训练信号，并鼓励它更显式地表征短程未来的结构。这在大规模下尤其有用，因为哪怕微小的 token 效率提升也很重要。

系统栈之所以能起作用，是因为 V3 是围绕硬件约束设计的，而不是忽视它们。FP8 降低了内存占用并提高了吞吐量；通信重叠隐藏了分布式 MoE 通信；专家放置和负载均衡减少了 all-to-all 瓶颈。换言之，V3 的模型质量与使模型在可接受成本下可训练的训练系统是不可分割的。

### 5. 为什么这项技术有局限

DeepSeek-V3 仍然主要是一个通用基础/对话模型，而不是一个完全优化过的推理模型。路线图下一篇论文说得清楚：R1 使用大规模 RL 从 V3-Base 激励出推理行为。如果 V3 已经解决了推理，R1 就没必要存在了。MTP 改善了训练信号和局部预测结构，但它并不能替代审慎的问题求解、证明搜索、工具使用或长周期规划。

V3 也继承了其底层效率栈的限制。MLA 降低了逐 token 的 KV-cache 宽度，但缓存仍然随上下文长度增长，这也是为什么 V4 后来走向了序列级 CSA/HCA 压缩。无辅助损失的负载均衡改进了 MoE 利用率，但它并没有在数学上保证理想的专家专业化或完美的路由。专家不均衡、专家冗余和专业化质量仍然是优化的结果，而非硬保证。

最后，V3 的效率有部分是系统特定的。它报告的成本依赖于精心设计的 H800 训练栈、低精度 kernel、通信重叠和专家并行基础设施。V3 是一个模型-系统的整体包；架构本身并不会自动把相同的成本剖面移植到每个硬件或软件环境中。它也仍然是文本中心的：如果没有额外的领域适配，它解决不了多模态感知、机器人、物理世界交互或特定具身推理。

**核心局限。**DeepSeek-V3 把高效的 MoE + MLA 架构 scale 成了一个强大的通用模型，但它并没有解决推理作为 RL 诱导行为、百万 token 上下文、硬专家解耦、多模态落地或完整训练系统的可移植性等问题。

### 6. 过渡到下一个瓶颈

V3 是前沿规模的基座模型。它提供了强大的通用、代码和数学能力，但预训练加普通对齐并不强迫模型在推理时把计算花在搜索、反思和验证上。R1 从 V3-Base 出发，把这种潜在能力变成了通过强化学习学到的推理行为。

## 创新 7：DeepSeek-R1——把能力转化为推理行为

### 1. 要解决的问题

DeepSeek-R1 解决的是 DeepSeek-V3 留下未决的瓶颈：一个强大的基座模型并不会自动成为强大的推理模型。V3 提供了广泛的知识、代码能力、数学能力和高效的 MoE 通用能力，但 next-token 预训练和普通指令微调并不天然产生审慎的多步推理。一个模型可以知道很多事实、模仿解答格式，但在需要探索、回溯、自我检查和持续中间推理的任务上仍然会失败。

关键问题不是简单地「怎么让模型知道得更多」。而是：怎么让模型在推理时把计算花在一个有用的推理过程上。DeepSeek-R1 的核心贡献在于证明了推理行为可以通过大规模强化学习被诱导出来。R1 论文引入了 DeepSeek-R1-Zero——从 DeepSeek-V3-Base 出发，仅用大规模 RL 而不经过监督微调作为预备步骤训练——以及 DeepSeek-R1，它加入了冷启动数据和多阶段训练流水线来解决 R1-Zero 的可读性和语言混合问题。

### 2. 核心技术思路

核心思路是把推理当作一种由 RL 诱导的行为，而不是仅仅从有监督的思维链样本中模仿出来的模式。R1-Zero 提出了一个干净的科学问题：如果一个强大的基座模型仅用基于结果的奖励来优化，推理行为能否在没有先教模型怎么写出推理链的情况下自然涌现？报告给出的答案是肯定的：R1-Zero 产生了长推理链和其他类推理行为，但它的输出在可读性和语言混合方面表现糟糕。

DeepSeek-R1 则把这一方法变得可用。它在 RL 之前加入冷启动监督数据，使用 GRPO 式 RL，合成推理和非推理数据，并施加额外的监督和 RL 阶段。概念上的动作是：用 RL 发现推理行为，但用监督数据和多阶段对齐让这些行为变得可读、稳定和广泛有用。公开的 R1 训练流水线摘要描述 R1-Zero 用 GRPO 和基于规则的奖励来训练，而 R1 则加入了冷启动数据、语言一致性奖励、合成推理数据、非推理数据，以及一个同时使用规则奖励和模型奖励的最终 RL 阶段。

### 3. 详细技术实现

R1 从 DeepSeek-V3-Base 出发，因此继承了 V3 的 MoE 架构和预训练分布。第一条分支 DeepSeek-R1-Zero 刻意跳过了监督微调，直接在基座模型上应用 RL。训练模板要求助手把推理放在 `<think>...</think>` 内，把最终答案放在 `<answer>...</answer>` 内，但除此之外避免施加过程约束，让模型可以探索自己的推理策略。

RL 算法是 GRPO。对每个问题 $q$，旧策略采样一组输出 $\{o_1,\ldots,o_G\}$。每个输出得到一个奖励，其优势在组内规范化：

\[A_i = \frac{r_i - \mathrm{mean}(\{r_1,\ldots,r_G\})}{\mathrm{std}(\{r_1,\ldots,r_G\})}.\]

策略目标使用 PPO 式裁剪加上针对参考策略的 KL 项，但避免了训练单独的 value 模型。对 R1-Zero，论文报告学习率 $3 \times 10^{-6}$、KL 系数 0.001、采样温度 1、每个问题 16 个输出、最大 rollout 长度在 step 8.2K 之前为 32,768 token、之后为 65,536、10,400 个训练步、每步 32 个不同问题、batch size 512。每 400 步，参考模型被替换为最新策略。为加速训练，每次 rollout 生成 8,192 个输出，分成 16 个 mini-batch，每个训练一个内层 epoch。

奖励设计在推理领域刻意基于规则。准确性奖励检查正确性：数学用 boxed 确定性答案，代码用编译器/测试用例结果，类逻辑任务用规则可验证答案。格式奖励鼓励所需的推理/答案标签。论文给准确性和格式奖励相同权重，并明确避免对 R1-Zero 推理任务使用神经奖励模型，因为它们在大规模 RL 中容易受到 reward hacking 的攻击。

DeepSeek-R1 本体则加入了一个多阶段流水线，让 R1-Zero 的原始行为变得可用。首先，DeepSeek 收集了数千条冷启动样本，带有对话式、人类对齐的长 CoT 推理，并对 DeepSeek-V3-Base 进行 SFT。然后跑第一个 GRPO 阶段，在推理 prompt 上训练，并加入语言一致性奖励来减少中英混合。这个阶段保留了 R1-Zero 的大部分 GRPO 设置，包括学习率 $3 \times 10^{-6}$、KL 系数 0.001、每个问题 16 个 rollout、最大长度 32,768、batch size 512，但新增了语言奖励，计算为目标语言单词在思维链中的比例。

接着，R1 使用了拒绝采样和再次 SFT。它采样推理输出，过滤/精炼它们，并把得到的推理数据与来自 DeepSeek-V3 式 SFT 的非推理数据混合，包括写作、事实性问答和通用指令任务。这产生的模型不仅是一个数学/代码推理器，也是一个通用助手。最后，第二个 RL 阶段在推理和通用 prompt 混合上训练。推理 prompt 继续使用规则奖励；通用 prompt 使用 helpfulness 和 safety 的奖励模型加上格式奖励。Helpfulness 奖励模型在 66K 个偏好对上训练，由 DeepSeek-V3 做评判；safety 奖励模型在 106K 个标记了安全/不安全的 prompt 上训练。在第二个 RL 阶段，温度降到 0.7，阶段跑 1,700 步，通用指令/偏好奖励仅在最后 400 步中引入以减少 reward hacking。

发布也包括蒸馏。更小的稠密模型从 Qwen 和 Llama checkpoint 初始化，并在 R1 生成的推理数据上训练。它们本身不运行完整的大规模 RL 流水线；它们通过从 R1 教师的监督蒸馏来继承推理行为。

### 4. 为什么这项技术能起作用

R1 之所以能起作用，是因为很多推理任务内部包含可用的强化信号。在数学和编程中，模型不需要人类对每个中间步骤做标注。它可以采样候选轨迹，而最终结果通常可以被自动检查：一个答案是否正确、一段程序是否通过测试、格式是否有误。这让基于结果的 RL 变得可扩展。

更深层的机制是，RL 改变了模型在推理时的行为。预训练教模型预测可能的续写；SFT 教它模仿期望的回复格式；RL 推它生成能带来奖励的轨迹。如果更长的探索、回溯、验证或自我修正增加了奖励，这些行为就会被强化。这就是为什么 R1-Zero 很重要：它表明推理链可以从奖励优化中涌现，而不仅仅是复制自监督样本。

GRPO 很重要，因为它降低了这个实验的成本。一个单独的价值模型在大规模下既昂贵又不稳定。组相对奖励让系统能够估计在同个 prompt 下哪些采样回复比其他回复更好。这是一个务实的近似：模型不需要对每个部分状态有一个绝对的价值估计；它只需要在采样结果之间有一个相对信号。

R1 起作用也是因为它修正了纯 RL 的失败模式。R1-Zero 发现了推理，但它的输出很难用：可读性差、语言混杂、呈现不稳定。冷启动数据在 RL 之前给了模型一个可读的格式。后来的 SFT 和最终 RL 阶段保住了推理能力，同时提升了可用性和通用指令跟随。换句话说，R1 结合了通过 RL 的发现和通过监督对齐的表现控制。

### 5. 为什么这项技术有局限

R1 的核心局限是，结果奖励并不保证忠实的推理。模型可以通过有缺陷的中间推理、幸运猜测、隐藏的捷径或基准特定的模式达到正确的最终答案。这与 DeepSeekMath-V2 后来强调的问题是相同的：答案级别的成功不是证明级别的正确。GRPO 在奖励廉价且可靠的场景下效果最好，比如很多数学和代码场景；而开放式推理、科学论证、法律分析和策略规划，如果不重新引入奖励模型误差或 reward hacking，很难给予奖励。

推理也需要控制。更多思考并不总是更好。[DeepSeek-R1 Thoughtology](https://arxiv.org/abs/2504.07128) 发现了一个「甜点区」，超过这个区域额外的推理时间反而会损害性能，还报告了 R1 会在更早的问题表述上反复沉思的情况。R1 类的模型必须不仅要学会思考，还要学会什么时候停下来、什么时候修正、什么时候改变策略。R1 论文本身在 R1-Zero 和 R1 之间的对比也指出了相关事实：纯 RL 可以发现推理，但冷启动数据和多阶段对齐是让推理变得可读和可用的必要条件。

更广泛的局限是，推理并不自动安全、多模态、工具落地，也并不唯一依赖于大规模 RL。[DeepSeek-R1 Thoughtology](https://arxiv.org/abs/2504.07128) 报告了安全漏洞；[OpenAI 的 o3/o4-mini 代](https://openai.com/index/introducing-o3-and-o4-mini/) 强调带图像和工具的推理；[Qwen3](https://arxiv.org/abs/2505.09388) 引入思考/非思考模式与思考预算机制；[s1](https://arxiv.org/abs/2501.19393) 表明精选样本加预算强制也能产生测试时 scaling。R1 是证明 RL 可以引发出推理行为的重要证据，但它不是推理验证、安全、工具使用或测试时计算分配的最终答案。

**核心局限。**DeepSeek-R1 证明了 RL 可以从强基座模型中引发出推理行为，但它没有解决忠实的推理验证、奖励泛化、推理长度控制、安全、多模态/工具落地的推理，以及如何最优分配测试时计算这些更广泛的问题。

### 6. 过渡到下一个瓶颈

R1 把 V3 变成了推理模型，但推理长度变成了系统问题。长 CoT、工具链、代码编辑历史、检索结果和 rollout 数据全都在膨胀上下文。这种压力暴露了 MLA 的极限：它压缩了 KV 宽度，但仍要为每个 token 存储一个状态。V4 瞄准的是推理的序列长度和缓存管理这一侧。

## 创新 8：DeepSeek-V4——让长周期智能可运作

### 1. 要解决的问题

DeepSeek-V4 解决的是 DeepSeek-R1 之后暴露的瓶颈：一旦模型可以推理、使用工具并作为 agent 运作，主要约束就变成了长周期计算的成本。R1 表明 RL 可以诱导出推理行为，但推理是昂贵的：长思维链、工具历史、搜索轨迹、代码编辑轨迹和大文档分析都会产生长上下文。如果模型必须对几十上百万 token 反复做注意力计算，限制因素就不再仅仅是参数数量或训练数据。限制因素变成了注意力计算、KV-cache 存储、内存带宽、缓存复用和 rollout 基础设施。

这是 DeepSeek-V2/V3 与 DeepSeek-V4 之间的关键区别。V2/V3 的 MLA 主要压缩的是逐 token 的 KV 宽度。这很强大，但缓存仍然随 token 数量增长。V4 瞄准的是下一个瓶颈：序列长度的 scaling 本身。其报告明确将 V4 定位为百万 token 上下文模型，并说明 V4-Pro 拥有 1.6T 总参数/49B 激活参数，而 V4-Flash 拥有 284B 总/13B 激活参数；两者都支持 1M token 上下文。在 1M 上下文中，报告声称 V4-Pro 仅需 DeepSeek-V3.2 单 token 推理 FLOPs 的 27% 和 KV cache 的 10%；V4-Flash 仅需 10% FLOPs 和 7% KV cache。

公开报道还将 V4 定位为包含 Pro 和 Flash 变体的预览版，拥有 1M token 上下文窗口。关于最强硬件/经济性的断言需要审慎表述：[Reuters 报道](https://www.investing.com/news/stock-market-news/chinas-deepseek-cuts-ai-model-price-by-75-in-challenge-to-global-rivals-432SI-4102398) 了 DeepSeek 对 V4-Pro API 的永久性 75% 降价，并指出 DeepSeek 并未披露降价是否由于华为昇腾 950 供应增加。V4 报告/模型卡，而非 Reuters，是模型架构和基准比较的主要来源。

### 2. 核心技术思路

DeepSeek-V4 的核心思路是全栈长上下文协同设计。V4 不仅是一个更大的 MoE 模型，也不仅是一个新的注意力模块。它围绕同一个目标重新设计了多层技术栈：让百万 token 的推理和 agentic 工作负载变得可负担。

在模型层面，V4 用混合压缩注意力取代了 V2/V3 式的长上下文瓶颈，结合了压缩稀疏注意力（CSA）和重度压缩注意力（HCA）。CSA 提供对压缩历史块的选择性访问；HCA 提供一条非常廉价的全局压缩路径。在残差/优化层面，V4 引入了 Manifold-Constrained Hyper-Connections（mHC）并使用 Muon 来提高稳定性和收敛性。在系统层面，它加入了融合专家并行 kernel、基于 TileLang 的 kernel 开发、确定性/批量不变 kernel、上下文并行、异构 KV-cache 布局，以及片上磁盘 KV-cache 复用。在后训练层面，它引入了专家训练加 On-Policy Distillation、FP4 量化感知训练、推理模式、DSML 工具调用、Quick Instruction token、容错 rollout 和 DSec 沙箱基础设施。

简而言之，DeepSeek-V4 把长周期智能当作一个模型-内存-kernel-训练-推理-agent-基础设施的整体问题来处理，而不是一个单纯的模型架构问题。

### 3. 详细技术实现

核心架构使用混合 CSA/HCA 注意力。CSA 首先将每小段 KV token 压缩成一个压缩 KV 条目，然后通过 Lightning Indexer 做稀疏选择。在报告的模型设置中，CSA 使用压缩率 4。V4-Pro 的稀疏注意力 top-k 是 1024；V4-Flash 是 512。因此，每个 query 不需要关注每一个历史块。它首先检索最相关的压缩块，然后只关注这些被选中的块。

HCA 更激进。它把更大块的 token 压缩成一个 KV 条目，报告压缩率为 128。与 CSA 不同，HCA 不做稀疏 top-k 选择；经高度压缩后，它可以在短得多的压缩序列上做稠密注意力。结果是一条廉价的全局记忆通路。这种混合设计让 V4 可以结合两种记忆：CSA 提供较高分辨率的选择性检索，HCA 提供低成本的宽泛上下文感知。

为避免丢失局部细节，CSA 和 HCA 都增加了对最近未压缩 token 的滑动窗口注意力分支。报告使用窗口大小 128。压缩可能损害局部句法和推理精度。V4 保持最近上下文的高分辨率，而压缩远距离上下文。

V4 还引入了 mHC，即 Manifold-Constrained Hyper-Connections。Hyper-Connections 将残差流展开为多个并行的通道，但朴素的 hyper-connections 可能不稳定。mHC 把残差映射矩阵约束到 Birkhoff 多面体上，使用 Sinkhorn-Knopp 投影，使得残差变换是非扩张的。其目的是让模型拥有更丰富的跨层信息路由，同时不允许残差信号爆炸。

在优化方面，V4 对大多数模块使用 Muon。Muon 通过混合 Newton-Schulz 迭代近似正交化更新矩阵。报告指出 Muon 改善了收敛和训练稳定性。V4 对 embedding、预测头、RMSNorm 权重和部分选定的 mHC 参数仍然使用 AdamW。

在基础设施方面，V4 构建了用于 MoE 专家并行的融合 kernel。系统将专家分成多波，使得一波的通信可以与另一波的计算重叠。报告声称在通用推理工作负载上实现了 1.50x 到 1.73x 的加速，在 RL rollout 和高速 agent 推理等延迟敏感场景中最高达到 1.96x。它还强调了用于融合 kernel 开发的 TileLang、确定性和批量不变 kernel、张量级 checkpointing、用于压缩注意力的上下文并行、定制 KV-cache 布局，以及用于共享前缀复用的片上磁盘 KV-cache 存储。

在后训练方面，V4 训练领域专家，然后通过多教师 On-Policy Distillation 将其整合。它还加入了 FP4 量化感知训练（用于 MoE 专家权重和 CSA indexer QK 通路）、三种推理模式、XML 式 DSML 工具调用模式、面向工具使用的交错思考、用于辅助任务的 Quick Instruction token，以及用于大规模 agentic 训练和评估的 DSec 沙箱基础设施。

### 4. 为什么这项技术能起作用

V4 之所以能起作用，是因为它攻击了长周期智能的实际成本结构。

CSA/HCA 起作用是因为百万 token 历史中包含巨大的冗余。并非每个历史 token 都需要保持全分辨率的 KV 条目。最近的 token 需要细粒度分辨率；远处的 token 通常只需要压缩检索或压缩全局摘要。CSA 通过检索相关压缩块保留了选择性访问。HCA 提供了宽泛但廉价的压缩覆盖。滑动窗口注意力保留了压缩会破坏的局部细节。

对于超长上下文，CSA/HCA 比单独 MLA 更强。MLA 压缩的是逐 token 的 KV cache 隐/通道维度，但仍然为每个 token 存储一个状态。CSA/HCA 通过沿序列维度压缩，来减少历史条目的有效数量。这就是为什么 V4 是 V2/V3 的天然继承者：它从隐维度的 KV 压缩走向了序列维度的上下文压缩。

mHC 之所以能起作用，是因为深层模型需要稳定的信息传播。如果残差路径太简单，可能限制跨层混合；如果太灵活，可能变得不稳定。把残差混合约束到一个非扩张的流形上，让模型拥有更丰富的路由，同时限制了信号放大。这在 V4 同时结合 MoE、压缩注意力、长上下文和大深度/大尺度的情况下尤其重要。

Muon 之所以能起作用，是因为大规模训练对更新几何是敏感的。矩阵级正交化更新比纯逐元素自适应更新可以改善条件数。这在万亿参数 MoE 训练中尤其重要，因为不稳定和各向异性的参数增长可能变得严重。

系统栈起作用是因为架构的收益不会自动转化为端到端速度。压缩注意力需要定制缓存布局和稀疏 kernel。MoE 需要专家分发和合并与计算重叠。FP4/FP8 需要精心设计的 kernel。OPD 和 RL 需要 rollout 服务和沙箱执行。V4 的核心工程论点是，长上下文推理不能仅凭一个模型 checkpoint 来解决；周围的训练和推理机器必须协同设计。

### 5. 为什么这项技术有局限

V4 的优势也是它的主要负担：它太复杂了。CSA、HCA、滑动窗口注意力、mHC、Muon、FP4 QAT、融合 MoE kernel、上下文并行、异构 KV cache、片上磁盘缓存、OPD、rollout 基础设施和沙箱，全都在互相作用。这使得系统难以推理、复现、干净地做消融或者移植到其他硬件。V4 报告自己也承认了这种复杂性，并表示未来工作将尝试把设计蒸馏成更核心的组件。

压缩风险是第二个主要限制条件。CSA 和 HCA 假设长历史通常可以被压缩而不丢失关键信息。这合理，但不是保证。精确检索、复制、罕见事实、形式依赖、代码库引用或对抗性放置的信息可能需要高分辨率记忆。模型可能接收了一百万 token，但在检索质量、规划连贯性或全局一致性上仍然退化。换言之，百万 token 上下文不等于百万 token 推理。

V4 仍然是一个预览阶段、系统依赖型架构，具有不均衡的前沿轮廓。它的性能依赖于精密的 kernel、缓存、推理、rollout 和硬件栈。V4 报告展示了强大的开源模型结果，但在某些事实性、推理和 agent 基准上，与顶级闭源模型的比较也有胜有负。R1 的早期局限也仍然存在：更好的长上下文基础设施本身并不保证忠实的推理、形式化正确性、安全或可靠的自我验证。

**核心局限。**DeepSeek-V4 让百万 token 的长周期智能大大更具可运作性，但它并没有完全解决信息丢失风险、忠实推理、系统可移植性、架构简单性，或在所有任务上与最佳闭源模型的对等。

### 6. 过渡到下一个瓶颈

V4 把路线图从「更多地推理」移到了「让长推理可运作」。它的开放问题不再是百万 token 上下文能否变得更便宜；而是在压缩下有多少精确信息能够存活、kernel/缓存栈的可移植性有多好，以及 agentic 推理在该规模下能被多可靠地验证。

## 技术深潜：CSA/HCA 多分辨率记忆

DeepSeek-V4 试图解决的核心问题不是简单地「如何让上下文窗口更长」。长上下文窗口只有在模型能够负担存储、读取和关注其中的历史信息时才有用。在标准 Transformer 中，每个之前的 token 都会贡献一个 key/value 条目给 KV cache。在自回归解码过程中，每个新 token 都必须与这段不断增长的历史记忆交互。如果上下文长度是 $T$，历史记忆随 $T$ 线性增长。早期 DeepSeek 模型中使用的 MLA 压缩了 KV cache 的逐 token 隐宽度，但仍然为每个历史 token 保留一个记忆条目。DeepSeek-V4 走得更远。CSA 和 HCA 压缩的是序列维度本身：若干 token 被融合成一个学到的压缩记忆条目。这就是从 V2/V3 到 V4 的本质转变。

理解 DeepSeek-V4 注意力的正确方式是把它看作一个多分辨率记忆系统。最近 token 保持高分辨率，因为精确的局部语法、格式化、变量名和即时推理步骤很重要。远处 token 通过压缩记忆条目来表示，因为大多数长程上下文不需要对每个未来 query 都以全 token 级精度来访问。CSA 提供了一个中等压缩的、由 query 检索的记忆。HCA 提供了一个高度压缩的、稠密的全局记忆。滑动窗口分支保留了精确的最近上下文。这不是对完美记忆的硬保证；这是一种学到的、有损的、多分辨率的近似，通过 next-token 预测和后训练目标端到端地训练出来。

从 Transformer 某层的 hidden state 序列开始：

\[H =
\begin{bmatrix}
h_0 \\
h_1 \\
\vdots \\
h_{n-1}
\end{bmatrix}
\in \mathbb{R}^{n \times d},
\qquad h_j \in \mathbb{R}^{d}.\]

这里 $n$ 是序列长度，$d$ 是隐维度。在普通注意力中，模型把 $H$ 投影成 key 和 value 并全部存储。CSA 的做法不同。它首先创建内容向量和压缩分数向量。内容向量是可能存活到压缩记忆中的信息。分数向量决定每个 token 和每个通道对压缩条目的贡献强度。

对 CSA，DeepSeek-V4 使用两个内容流：

\[C^a = H W^a_{KV},
\qquad
C^b = H W^b_{KV},
\qquad
W^a_{KV}, W^b_{KV} \in \mathbb{R}^{d \times c}.\]

对 token $j$，这意味着：

\[C^a_j = h_j W^a_{KV},
\qquad
C^b_j = h_j W^b_{KV},
\qquad
C^a_j, C^b_j \in \mathbb{R}^{c}.\]

这两个流不是普通的注意力头。它们是 token 贡献给相邻压缩条目的两种方式。如果序列简单地被切成不重叠的四 token 块，跨越边界的短语、代码表达式或推理单元就可能被割裂。DeepSeek-V4 通过同时从当前块和前一个块构造每个 CSA 压缩条目来避免这一点。一个流让 token 贡献给压缩边界的一侧，另一个流让它贡献给相邻的压缩条目。这提供了有重叠的压缩，同时仍然每 $m$ 个 token 产出一个压缩条目。

分数流类似地产生：

\[Z^a = H W^a_Z,
\qquad
Z^b = H W^b_Z,
\qquad
W^a_Z, W^b_Z \in \mathbb{R}^{d \times c}.\]

对 token $j$：

\[Z^a_j = h_j W^a_Z,
\qquad
Z^b_j = h_j W^b_Z,
\qquad
Z^a_j, Z^b_j \in \mathbb{R}^{c}.\]

$Z$ 向量不作为记忆内容存储。它们是用于产生压缩权重的 logit。细节很重要：$Z$、$S$ 和 $C$ 都有通道维度 $c$。压缩不是每个 token 一个标量的重要性分数。它是一个逐通道的混合决策。压缩向量的不同维度可以从不同的源 token 中选择信息，这使得 CSA 比平均池化或标量 token 打分更具表达能力。

DeepSeek-V4 使用 CSA 块大小 $m = 4$。对于压缩条目 $i$，当前块是：

\[B_i = \{mi, mi+1, \ldots, m(i+1)-1\}.\]

前一个块是：

\[B_{i-1} = \{m(i-1), m(i-1)+1, \ldots, mi-1\}.\]

CSA 使用当前块的 $C^a$ 和前一块的 $C^b$ 来形成压缩条目 $i$。在混合内容之前，它先把 $Z$ logit 转换为规范化权重。它拼接当前块的 $Z^a$ logit 和前一块的 $Z^b$ logit，加上可学习的位置偏置，然后对 $2m$ 个候选 token 位置按每个通道执行 softmax：

\[\left[
S^a_{mi:m(i+1)-1};
S^b_{m(i-1):mi-1}
\right]
=
\operatorname{Softmax}_{\mathrm{row}}
\left(
\left[
Z^a_{mi:m(i+1)-1} + B^a;
Z^b_{m(i-1):mi-1} + B^b
\right]
\right).\]

这就是 CSA 压缩的核心。$Z$ 给出未规范化的压缩 logit。$B^a$ 和 $B^b$ 注入了局部位置信息，因为 token 在压缩窗口内的位置是重要的。softmax 将这些 logit 转换为 $S$，即规范化的混合权重。由于 softmax 是在候选 token 位置上施加的，这些权重决定了哪些 token 位置对压缩记忆条目的每个通道做出贡献。

CSA 随后形成压缩内容向量：

\[C^{\mathrm{Comp}}_i
=
\sum_{j=mi}^{m(i+1)-1} S^a_j \odot C^a_j
+
\sum_{j=m(i-1)}^{mi-1} S^b_j \odot C^b_j.\]

乘法 $\odot$ 是逐元素的。如果 $S_j$ 是标量，token $j$ 要么对整个压缩向量贡献强，要么弱。但因为 $S_j \in \mathbb{R}^{c}$，token $j$ 可以对其中的某些特征通道贡献强，对另一些贡献弱。一个数字 token 可能占据数字相关的通道。一个变量名可能占据标识符通道。一个结构 token 可能占据语法或格式化通道。压缩器不仅仅是在决定哪些 token 存活；它在学习如何在局部压缩窗口内跨 token 分配特征通道。

对 $m = 4$，压缩条目 $i$ 从八个候选 token 表征中计算出来：四个来自前一块通过 $b$ 流，四个来自当前块通过 $a$ 流。但压缩条目仍然是每四个 token 产生一个，因为相邻压缩条目有重叠。这就是为什么压缩比约为 $4\times$ 而非 $8\times$。有重叠的设计在不过度削减压缩条目数量的同时，减少了边界伪影。

走到这里，CSA 已经把序列长度从 $n$ 个 token 级 KV 条目缩减到了约 $n/m$ 个压缩条目。$m = 4$ 时，一百万 token 上下文仍然产出约 250,000 个压缩条目。这远比一百万小，但对每个解码步做稠密注意力来说仍然太大。CSA 通过 Lightning Indexer 增加了稀疏检索。

Lightning Indexer 从历史压缩块中创建压缩 indexer key，并从当前 token 创建 query 侧的 indexer 表征。概念上，对于当前 query token $t$，它计算 query 与每个历史压缩块之间的分数：

\[I_{t,s} = \operatorname{score}\left(q^I_t, K^{I,\mathrm{Comp}}_s\right).\]

论文实际使用的分数涉及多个 indexer query 头、可学习的头权重和 ReLU 变换的点积，但功能含义是这样的：$I_{t,s}$ 估计压缩块 $s$ 对 token $t$ 是否相关。CSA 然后选择 top-$k$ 压缩条目：

\[\mathcal{S}_t = \operatorname{TopK}(I_{t,:}).\]

对 DeepSeek-V4-Pro，$k = 1024$。对 DeepSeek-V4-Flash，$k = 512$。这意味着 CSA 不在 250,000 个压缩条目上运行主注意力。它首先检索一个依赖 query 的子集，然后仅在这个子集上运行注意力：

\[\operatorname{CSA}(t)
=
\operatorname{Attn}
\left(
q_t,
\left\{C^{\mathrm{Comp}}_s \mid s \in \mathcal{S}_t\right\}
\right).\]

这解释了「压缩稀疏注意力」这个短语。它是压缩的，因为 token 块被合并成了压缩条目。它是稀疏的，因为 query 只关注 top-k 压缩条目而非所有压缩条目。压缩减少了记忆的长度；稀疏检索减少了注意力计算。

HCA（重度压缩注意力）更简单。它使用同样的可学习块压缩的基本思想，但压缩比大得多。不使用 $m = 4$，DeepSeek-V4 使用 $m' = 128$。投影是单内容流和单 logit 流：

\[C = H W_{KV},
\qquad
Z = H W_Z.\]

对每个 128-token 块，HCA 把 $Z$ 转换为 softmax 权重，并用它们来组合内容向量：

\[S_{m'i:m'(i+1)-1}
=
\operatorname{Softmax}_{\mathrm{row}}
\left(
Z_{m'i:m'(i+1)-1} + B
\right),\]

\[C^{\mathrm{Comp}}_i
=
\sum_{j=m'i}^{m'(i+1)-1} S_j \odot C_j.\]

$m' = 128$ 时，一百万 token 仅变成约 7,812 条压缩条目：

\[\frac{1{,}000{,}000}{128} \approx 7{,}812.\]

因为压缩后的序列现在短得多，HCA 不需要 top-k 稀疏检索。它可以负担对所有重度压缩条目的稠密注意力：

\[\operatorname{HCA}(t)
=
\operatorname{Attn}
\left(
q_t,
\left\{
C^{\mathrm{Comp}}_0,
C^{\mathrm{Comp}}_1,
\ldots,
C^{\mathrm{Comp}}_{\lfloor n/m' \rfloor}
\right\}
\right).\]

CSA 和 HCA 的不同之处在于如何用精度换取成本。CSA 使用中等压缩后跟稀疏检索，更适合相对特定的远处信息。HCA 使用激进压缩后跟稠密注意力，更适合低分辨率全局上下文。不应把 HCA 描述为有保证的「主题记忆」，因为论文并没有证明这一点。更精确的表述是：因为 HCA 把 128 个 token 压缩成一个向量，它天然不能保留所有 token 级细节；它在结构上偏向粗粒度的聚合信息。

滑动窗口分支是必要的，因为 CSA 和 HCA 都是有损的。最近的上下文往往需要精确记忆。下一个 token 可能依赖于紧邻的句法、标点、变量名、缩进或局部推理步骤。DeepSeek-V4 增加了一个局部未压缩注意力分支，窗口大小 $n_{\mathrm{win}} = 128$。模型精确地关注最近的 token，而对远处的 token 使用压缩记忆：

\[O_t = O^{\mathrm{local}}_t + O^{\mathrm{compressed}}_t.\]

论文的实现还包括共享 key-value 的 MQA 式注意力、分组输出投影、部分 RoPE 处理、query/KV 归一化和注意力 sink，所以实际层比这个简单求和要更复杂。但记忆层级可以被这个表达式所捕捉：局部精确注意力提供高分辨率的最近上下文；CSA/HCA 提供压缩的长程上下文。

值得辩护的假设不是「填充词可以被删除」。更强的假设是，并非所有历史 token 状态都需要对每个未来 query 以相同的分辨率来呈现。在语言、代码、文档和推理链中，精确的局部上下文非常重要，而远处的上下文往往通过选定区域或聚合状态来发挥作用。CSA/HCA 把这个假设直接编码进了架构。CSA 保留中等压缩的记忆并让每个 query 检索相关块。HCA 保留高度压缩的全局路径。滑动窗口保留了精确的局部依赖。

这种可学习的压缩是合理的，因为它是端到端训练的。压缩权重不是由人类熵检测器选定的。模型在 next-token 预测和后训练目标下学到了 $W_{KV}$、$W_Z$、位置偏置、indexer 投影和注意力投影。如果压缩破坏了预测所需的信息，损失就会推动模型去改变它如何往 $C$ 中写入信息、如何通过 $Z$ 给 token 打分，以及如何通过 Lightning Indexer 检索块。压缩器是一个学到的记忆写入机制。

效率的故事现在很清楚了。MLA 降低了每个 token 缓存状态的宽度：

\[T \cdot d_{KV} \longrightarrow T \cdot d_{\mathrm{latent}}.\]

而 CSA 和 HCA 攻击的是 $T$：

\[T \longrightarrow \frac{T}{m},
\qquad
T \longrightarrow \frac{T}{m'}.\]

CSA 还进一步缩减了核心注意力集合：

\[\frac{T}{m} \longrightarrow k.\]

这就是为什么 DeepSeek-V4 可以瞄准百万 token 上下文。报告称，在一百万 token 时，V4-Pro 仅需 DeepSeek-V3.2 单 token 推理 FLOPs 的 27% 和 KV cache 的 10%；V4-Flash 仅需 10% 的 FLOPs 和 7% 的 KV cache。

局限同样重要。CSA/HCA 是有损的。它们不保证每个远处的事实、数字、变量、表格单元、证明依赖或精确引文都能在压缩中存活。当压缩表征丢失了相关信息，或者 Lightning Indexer 未能选中正确的块时，CSA 就可能失败。当 128 个 token 包含多个不同事实而无法全部塞进一个压缩向量时，HCA 就可能失败。这个架构不是完美的百万 token 记忆。它是一种学到的多分辨率近似，用精确度换取了成本。

干净的解读是：DeepSeek-V4 用学到的多分辨率记忆取代了均匀的历史记忆。滑动窗口注意力保持最近 token 的精确性。CSA 将小的重叠 token 区域写入压缩条目，并为每个 query 检索最相关的那些。HCA 将大的 token 区域写入高度压缩的条目，给模型一条廉价的稠密全局路径。这个设计攻击的是真正的百万 token 瓶颈：不仅是 KV cache 的宽度，而是必须存储和读取的历史状态的数量。当远处上下文可以在块级别被压缩或检索时，它起作用。当远处的精确 token 级保真度必不可少时，它失败。

## 技术侧栏：超越加法恒等式——Moonshot AttnRes 与 DeepSeek mHC

十多年来，残差连接 $x_{l+1} = x_l + F(x_l)$ 一直是深度学习的基础基石。由 ResNet 普及并被 Transformer 继承，这个简单的加法操作防止了梯度消失，让网络可以扩展到数百层。

但随着 LLM 走向万亿参数 MoE 系统、极端深度和百万 token 上下文，经典的残差流开始显得像一个结构瓶颈。一个单一的 $d$ 维向量能承载的信息是有限的。当深层不断把新的变换注入同一个数学桶里，早期层的特征就可能被稀释、覆盖，或在数值上变得难以提取。

2026 年的两条架构路线从正交的几何角度攻击了这个问题：Moonshot AI 的注意力残差（AttnRes）和 DeepSeek-V4 的流形约束超连接（mHC）。两者都超越了被动的加法积累，走向主动的结构化路由，但它们沿不同的轴来路由信息。

### Moonshot 注意力残差：选择性的搜索引擎

[Moonshot 的 Attention Residuals](https://arxiv.org/abs/2603.15031) 解决的是论文称之为 PreNorm 稀释的病理。在一个深层 PreNorm Transformer 中，后续层可能需要那些远在早期层就提取出的原始句法或 token 特征。在标准残差积累下，这些早期特征被混合进了不断增长的后续层输出中。为了让早期特征在深层能够被「听见」，后续层可能需要发出越来越大的输出，造成幅度增长和不均匀的梯度分布。

AttnRes 把深度轴变成了一个动态数据库。每层不再盲目继承上一层的残差流，而是学到一个伪 query 向量，并在历史层输出上计算 softmax 注意力分布：

\[h_l = \sum_i \alpha_{i \to l} \cdot v_i.\]

这里 $\alpha_{i \to l}$ 是分配给过去层 $i$ 的规范化相关性权重。直觉很简单：AttnRes 就像在深度上运行的按需检索引擎。如果第 80 层需要第 3 层提取的原始特征，它不必依赖那个特征在 4 到 79 层的累积噪声中存活下来。它可以给第 3 层分配一个高相似度分数，并直接取回那个历史表征。

这让 AttnRes 成为一种纵向残差路由机制。它沿层的时间线向后看，并选择性地复用早期状态。代价是朴素的 AttnRes 会增加激活内存和通信，因为深层可能需要访问很多先前层的输出。Moonshot 引入了 Block AttnRes，将层分组为局部块，这样回溯窗口就有界了，激活缓存的额外开销也保持在可控范围。

### DeepSeek mHC：多车道高速路

Moonshot 沿深度向后看，而 DeepSeek 沿宽度向外看。标准残差流把通信限制在一条 $d$ 维的车道上。Hyper-Connections 把这条公路扩展为多条并行残差流，让信息可以通过若干通道流动，而不是被挤在一个向量里。

危险在于不稳定。如果每层用一个无约束的可学习矩阵自由混合并行流，哪怕微小的数值不平衡也会在深度上乘性地加剧。信号方差可能爆炸，梯度可能 blow up，更丰富的多车道残差结构就变得不可训练。

DeepSeek-V4 的 mHC 通过使用 Sinkhorn-Knopp 算法把残差混合矩阵投影到 Birkhoff 多面体上来稳定这条多流高速路。在实际操作中，路由矩阵被强制为双随机的：每行和每列之和均为 1。由于双随机矩阵的乘积仍然是双随机的，很多层上的复合特征路由映射保持了质量守恒：

\[P_{i \to L} = \prod_j H_{\mathrm{res}}^{(j)}.\]

直觉就是一条完全平衡的多车道高速路。mHC 不像 AttnRes 那样动态地跳回到任意旧层。相反，它做的是在多条残差车道上逐层的局部路由决策。数学约束使这些路由决策保持有界，这样特征就可以在深度上被重排、保持和重组，而不会丢失信号质量或出现爆炸性的方差。

### 结构对比

| 维度 | Moonshot 注意力残差 | DeepSeek mHC |
|------|---------------------|-------------|
| 路由几何 | 纵向：跨越深度跳跃，检索先前层状态 | 横向：将残差流扩展为多条宽度方向的车道 |
| 相关性原则 | 相关性驱动：对历史激活做 softmax 相似度 | 约束驱动：通过双随机投影限定可学习的路由 |
| 数学锚点 | Softmax 规范化的凸组合 | 通过 Sinkhorn-Knopp 的 Birkhoff 多面体投影 |
| 修复的主要病理 | PreNorm 稀释和历史特征冲刷 | 多流残差路由中的方差爆炸 |
| 系统瓶颈 | 跨大量先前层的激活缓存 | 维护和混合多条残差车道带来的 IO 压力 |
| 解决方案 | Block AttnRes 限制回溯窗口 | 融合 kernel 和选择性重计算降低内存流量 |

### 硬件与系统的权衡

两种方法都打破了标准残差加法的近乎零成本特性。AttnRes 创造了一堵激活缓存墙：如果每层都对很多先前层的输出做注意力，模型必须存储并在 HBM 和流水线边界之间搬运大量历史激活。Block AttnRes 是务实的答案：把深度上的注意力限制在局部块内，使得选择性检索是可能的，同时不会带来无界的激活流量。

mHC 创造了另一种 IO 约束的内存墙。维护多条残差车道意味着更多的读取、写入、投影和归一化。DeepSeek 的答案是硬件-软件协同设计：把流投影、归一化和 Sinkhorn 式缩放融合进定制 kernel，并使用选择性重计算——在前向过程中丢弃昂贵的中间多车道状态，在反向过程中重新计算。这在保留了更丰富的残差路由结构的同时，降低了显存压力。

### 搜索引擎 vs. 有界高速路

关键的区别是几何上的。Moonshot AttnRes 把深度当作可搜索的记忆时间线。它问的是：这一层应该检索之前哪一层的状态？DeepSeek mHC 把宽度当作受约束的路由织网。它问的是：信息应该如何跨多条并行残差车道流动，同时保持信号质量？

在更广的 DeepSeek 路线图中，mHC 完美地契合了 V4 的主题。一旦长周期推理、压缩注意力、MoE 路由和 agentic rollout 让模型变得更深、系统更重，残差流本身就变成了效率问题的一部分。V4 的答案不仅仅是压缩上下文；它也加固了穿过模型内部的信息高速路。

## 跨论文的技术线索

### 1. 参数和隐容量控制

DeepSeekMoE 开启了这条路线图，把总容量和激活计算分离开来。细粒度路由专家提高了路由分辨率；共享专家为高频特征创建了公共通路。V2、V3、Coder-V2、R1 和 V4 继承了这个基本赌注：模型容量的增长应该快于逐 token 计算。

### 2. 领域基的塑造

DeepSeek-Coder 和 DeepSeekMath 表明，只有学到的特征基是在正确的结构上训练时，容量才有用。仓库级代码数据教的是软件组织；数学继续数据教的是符号和推导模式。Coder-V2 然后把同样的原理应用到了 V2 的经济型骨干之上。

### 3. KV 宽度和序列长度的压缩

V2 引入了 MLA，沿隐/通道维度压缩逐 token 的 KV 表征。V4 通过 CSA/HCA 走得更远，压缩序列维度本身，并在多个分辨率上检索压缩记忆。这就是从更廉价的长上下文推理到百万 token 记忆系统的递进。

### 4. 推理轨迹的扩展

DeepSeekMath 引入了 GRPO 作为一种低成本来改进可验证推理的方法。R1 把这个机制变成了从 V3-Base 诱导长推理行为的核心手段。成本于是从模型参数转移到了轨迹上：更多思考、更多 rollout token、更多工具历史、更多 KV-cache 压力。

### 5. 残差与内部路由

V4 的 mHC 表明残差流本身变成了 scaling 瓶颈。路线图不再只是把 token 路由给专家，或把 query 路由给记忆块；它也在模型内部沿着深度和宽度路由信息。Moonshot AttnRes 的侧栏通过展示一种正交的深度方向检索方法来进一步说明了这一点。

### 6. 系统协同设计

V3 和 V4 清楚地表明，DeepSeek 的优势不仅是模型架构。FP8/FP4 精度、DualPipe、all-to-all kernel、融合 MoE kernel、确定性 kernel、checkpointing 策略、缓存布局、rollout 基础设施和沙箱执行——这些都被当作模型创新路线图的一部分。

## 结语：以效率为路线图

DeepSeek 的技术路线图从稀疏参数容量和领域塑造的表征出发，走到 KV-cache 压缩、前沿级系统工程、推理轨迹 scaling、序列级记忆压缩，最后到面向长周期智能的残差和内部路由。

重要的模式是，DeepSeek 并不把 scale 当成一个单一的旋钮来拧。每个阶段问的是系统的哪一部分变得浪费了：未被使用的稠密参数、通用数据、膨胀的 KV cache、不稳定的 MoE 路由、肤浅的推理轨迹，还是百万 token 的记忆。答案总是某种形式的选择性分配。只路由有用的专家。只缓存有用的隐状态。只检索有用的压缩块。把推理 token 花在奖励能塑造它们的地方。在不让信号爆炸的前提下保留残差信息。

这就是效率的护城河。它不仅意味着更低的训练成本，也不仅是聪明的压缩手法。它是一种习惯——把每一堵 scaling 的墙都变成一个架构或系统问题。这条路线的意义在于，它把前沿 AI 的进步重新框定为跨越模型、数据、内存、训练、推理和 agent 基础设施的优化问题。DeepSeek 的赌注是，智能不一定要用纯粹的暴力来购买；它也可以通过更好的瓶颈解除来设计出来。
